# Item acquisition navigation

Use when adding custom StarPoint CN items, adding/changing/removing acquisition sources for existing items, or fixing “入手方法” results. The user explicitly requested this standing check on 2026-09-12. It applies to the affected reward change; it does not require a global historical audit for unrelated text/art edits or authorize extra deployment work.

## Why an item-key check is insufficient

The .106 incident began with six mech steam cores present in custom hard-multiplayer rewards but absent from `master/search/item_quest_search.orderedmap`. Adding eight entirely missing keys repaired that first symptom. A wider check then found existing items missing Fantasy fixed-material and Deep Abyss final rewards, plus item 14040 missing 28 Expert first-SS sources.

The completed repair added 152 source rows across 55 items: 11 new keys and 44 extended keys. These are historical incident counts, not future coverage targets. A check of `item_id in search` would still have accepted the incomplete eight-key patch. The invariant is that each actual supported item–source relationship has the correct navigation entry.

## Establish the actual acquisition contract

- Start from the current winning public runtime accessors, merged base/extension configuration and settlement logic. Do not infer drops only from client descriptions or a base JSON overridden at runtime.
- Enumerate the affected ordinary score/rare drops, fixed material schedules, random pools, per-round and final-run rewards, first-clear/first-SS rewards, shops and box pools. Classify each source before choosing a destination; a static quest index cannot stand in for shop filtering or an unsupported mission/ranking destination.
- Distinguish repeatable, random and one-time rewards. Preserve actual amounts, conditions and unlocks; editing the search index must not silently alter rewards. If a sorting weight represents expected quantity, include the selection probability. For the demonstrated six-item ether pool, average 2.5 picks times average 325 units divided by 6 gave 135.416666667 per item, rather than 325 guaranteed units for every item.
- First-SS sources in the incident yield 3 units once per quest. The static index cannot remove an already claimed source per player; describe the one-time restriction accurately and preserve native unlock/challenge limits. Zero sorting weight was accepted by the inspected client, but recheck the reader when client behavior changes.

## Resolve and validate the destination

- Read effective master data from the pristine baseline plus enabled patch chain. Update the relevant item/equipment search structure or server acquisition route by source type. Preserve unrelated existing rows and order; explicitly handle sources removed by the requested reward change instead of blindly accumulating stale entries.
- Use the client master reference enum and actual table keys. In the inspected accepted client, HardMulti uses reference kind 18, Expert uses 12, and Rush uses 16. Server quest category 26 is not the client HardMulti enum. Expert display/group columns are not reference keys. These values are evidence from that client, not permission to bypass future reader verification.
- Validate target existence, selection/visibility, prerequisite quests, availability and single/multiplayer routing. The native acquisition scene limits visible results to five and applies filters; a serialized row does not prove it will always be displayed. Do not add inactive or hidden training stages simply because a numeric quest ID resolves.
- Trace the event-container gate as well as each quest. The 2026-09-12 Android regression persisted after a confirmed .106 download: all six gear/core source pairs referenced valid permanent HardMulti quests, but `ItemHowToGetQuestSearcher.getAvailableQuestLogic` only admitted ordinary/side-story event IDs. Permanent mechs 1001–1006 and Rush 700098/700099 live in `event_folder_events`, outside `event_list`, and were rejected before quest checks. Reproduce membership through the effective tables and actual reader. Preserve folder unlocks, event periods and native quest filters; do not restore duplicate event-home banners by blindly adding folder contents to `event_list`. This failure requires a client filter repair, not another identical CDN index. The Android candidate in `client-patch/item-source-folders` adds only the missing folder fallback; its offline checks are not device acceptance and do not imply an iOS port.
- Validate resources used by the actual newly reached UI. `ItemThumbnailView` can asynchronously load a thumbnail; `DropItemContentsView` synchronously requires a preloaded `smallVectorIconId`. Some ordinary items legitimately have no optional small icon. Do not add them to a stage material bar or rewrite their icon fields merely to satisfy an overbroad checker. Follow [client-cdn-resource-safety.md](client-cdn-resource-safety.md) when these readers are affected.

## Validate and deliver the same change

- Build expected item–source pairs independently from the final index, using the runtime contract above. Check each expected relationship after serialization, not only item-key counts or total row counts. Validate old unaffected rows, IDs and icon references as well.
- For a regression fix or changed generator, exercise the demonstrated failure: remove a newly added source from an item that still has other valid rows; completeness must fail. Also reject wrong target/reference types and changed one-time semantics where relevant. Reuse focused tests rather than rebuilding unrelated gameplay or save systems.
- Repository examples under `F:/codex/startpoint-cn-private-clean/`: `tools/lens-integration/export_acquisition_contract.cjs`, `complete_how_to_get_sources.py`, `test_complete_how_to_get_sources.py`, and `tests/how-to-get-route.test.js`. Evidence is in `assets/asset-patch/audit/mech-item-sources-1.4.106/`. The .106 publisher locks the exact unpublished preimage and intentionally rejects reuse after replacement; adapt from the current chain, never bypass its hash protection.
- If client search/master bytes change, deliver a CDN delta plus manifest as part of the authorized resource work. Inspect the current terminal version rather than reusing .106. Preserve published archive bytes; the historical .106 replacement had explicit user authorization and was unpublished. No APK/IPA rebuild is needed when the existing client already supports the destination and common resource format, but verify that condition.
- Include server source and verified build outputs when server acquisition behavior changes. A CDN ZIP alone cannot deploy a server route fix. For a later authorized cloud overlay, keep inner active ZIPs byte-for-byte, exclude outer loose `production` resources, and consult the repository's pending-cloud list.
- Report actual coverage, files and verification limits. Static index/reader checks and HTTP byte checks are not device acceptance. Record any unsupported source honestly instead of fabricating a battle entrance. Continue the repository's separate save-impact assessment and deployment authorization rules.
