## Baseline, donor inputs, and patch output

- Ordinary CDN generation keeps encoding/root, ZIP/manifest and affected terminal-resource checks. HTTP probes are for concrete download/version faults, affected HTTP routes/admission, a needed distribution check without an available client, or explicitly requested HTTP acceptance; they are not automatic steps for every edge or server start. When a client will download and verify the same batch, do not duplicate its download. Reuse `tools/cdn-http-probe.cjs` instead of writing a batch probe; service readiness is sufficient to hand over a start-only request. A requested range starts at the device's actual `RES_VER` or an explicitly supplied resource version, not an assumed manifest predecessor or APK/IPA build baseline.

- On this workstation, use the existing port 8001 service and the source repository's active manifest for all live resource tests. Do not introduce a proxy, rewrite advertised resource versions, or maintain a separate temporary CDN chain. Offline fixtures are build inputs only. For consolidation, include every final resource source, including legacy supplements previously delivered outside the manifest; prove their terminal bytes are in the single published archive before retiring that delivery path. Keep compatible client resource names unless a rename is specifically required. The demonstrated Inaho regression omitted 12 effect files and seven updated voices from a previously active supplement while reporting the character as consolidated.

- Follow the repository's pristine-CDN boundary: `.cdn/` is read-only original resource data, not a landing directory for new patches. Resolve its junction/symlink target before any write plan.

Reuse that result within this task while the manifest, enabled archive inputs and publication target are unchanged; do not replay the same chain per resource or substep. A changed input or contradictory result requires the affected chain check again. Never select a tail from an incident's remembered version; preserve published archive bytes unless consolidation or replacement is explicitly requested.
- When replacing or consolidating custom patches, confirm that the actual server download route filters active-directory ZIPs through enabled manifest `archive/chain` entries. A directory scan can continue publishing superseded, disabled or unregistered archives; removing a manifest entry alone then fails to retire it. Keep manifest-filtered download lists and size totals consistent on both platforms and verify terminal member bytes; use actual HTTP checks under the triggers above. ## Small item icons require a preloaded texture, not just a PNG

- Trace the failing reader before choosing a repair. `DropItemContentsView.addDropItemList` reads `smallVectorIconId` and immediately calls `ViewAssetContainer.getImage`; it does not trigger an asynchronous image load. C8004 on this path means the texture is not in the scanned caches. It does not by itself prove an incomplete client upgrade or a missing archive member.
- Inspect the final item row, the effective atlas/PNG pair, and the scene's asset groups together. An independently downloadable PNG with the right hashed filename is not sufficient loading closure for a synchronous reader.
- In the demonstrated Deep Abyss case, both thumbnail and small-icon columns used the full names `item/materials/mod/abyss/abyss_coin`, `abyss_core`, and `abyss_seal`. Normal post-tutorial UI scenes load the common Item group, and `AssetResolver` loads `item/sprite_sheet` / `item_sec/sprite_sheet`; atlas `n` values register full-path subtextures. Appending the three same-name frames to the effective `item/sprite_sheet` pair repaired cache availability without changing the item table or artwork.
- Prefer the already loaded atlas whose namespace and dimensions fit the existing references. Do not automatically redirect every small icon to `item_icon`, replace custom art with an unrelated official icon, or alter item tables when the existing full-path references can be satisfied correctly. Recheck the loader for a different client build or a pre-tutorial scene.
- Preserve every existing frame's name, geometry, rotation/trim metadata, and rendered RGBA pixels. Append only the requested frames in a transparent extension with gutters; keep the original source pixels and dimensions unless resizing was requested. Do not reconstruct the atlas from an older baseline and lose previously added ticket or weapon icons.
- Verify after serialization: existing frame metadata and pixels unchanged; new names unique; rectangles in bounds and non-overlapping; new crops equal their source PNGs; current item references resolve into a loaded group; only the intended archive members changed. Record source and output hashes. Static archive/loader evidence is not device UI verification.
- For this atlas repair, no `trimmed_image` or extra standalone-PNG change was needed: the loaded atlas already supplies safe subtextures. Do not treat adding a trim row alone as a solution to an absent preload.

## C8105: validate the stored PNG signature before publishing

- When C8105 contains `signature error: not png file.` and the stack reaches `FileReader.convertEncryptedFile` / `fileFaker.converter.PNGConverter.decode`, inspect the exact effective payload and the client's reader contract. This diagnosis is specific to that stack; C8105 alone is not proof of a PNG-header error.
- The demonstrated shop reader requires the stored signature `89 70 6e 67 0d 0a 1a 0a` (lowercase `png`). Ordinary PNGs begin `89 50 4e 47 0d 0a 1a 0a` (uppercase `PNG`). Encode ordinary donor PNGs with `wf_assets.png_encode` before archiving. For this format, only offsets 1, 2, and 3 change; preserve all remaining bytes, dimensions, color mode, alpha, and pixels.
- **Shared Android/iOS PNG does not mean an unencoded donor PNG is publishable.** The .100 shop-banner publisher preserved ordinary donor bytes and checked hashes/dimensions, but omitted the stored-signature contract. Both affected banners consequently failed in the strict client decoder. Asset root and platform pairing checks do not replace storage-format checks.
- For each outgoing PNG consumed by this reader, require `wf_assets.PNG_FAKE`, then call `wf_assets.png_decode_stored` and fully load the resulting PNG. Verify the decoded bytes equal the intended donor and check dimensions, mode, and pixels. Repeat strict decoding on members read back from the final ZIP and, during authorized runtime testing, from the advertised download URL. Reject standard signatures and malformed images before activating the manifest.
- `wf_assets.png_decode` is intentionally lenient for editing: it accepts an ordinary PNG unchanged. It is not a publication gate. A successful Pillow preview, correct filename, ZIP CRC, or donor SHA alone also cannot prove that the client's strict decoder will accept the stored file.
- If clients have already downloaded the bad version, append a new edge after the verified active tail so they receive corrected bytes. In this incident the repair is .100 -> .101 with only the two encoded banners; keep published .100 ZIPs immutable. Do not turn these historical version numbers into defaults for future work.
- Preserve a regression that rejects an ordinary PNG accepted by the editing helper and proves strict round trips for RGB and RGBA donors. The repository's `tests/test_png_storage.py` and `publish_shop_banner_png_encoding_1_4_101.py` demonstrate this check. Static decoder parity and successful HTTP delivery still leave device UI acceptance to actual testing.

## Android/iOS: distinguish shared PNGs from platform textures

- Check `FileReader`'s actual path rules. The ordinary `item/` PNG and atlas used above are common resources consumed by both Android and iOS; they do not use platform-specific ATF branches. Publishing both common members is the iOS counterpart too—do not omit iOS consideration, but do not invent an unnecessary iOS conversion.
- Shared image format does not establish a common storage root. Tutorial-bundle resources, including the `character_pedestal` inline-icon atlas, follow the native reader's platform-root selection; an `upload` PNG or an Android-only atlas update cannot satisfy an iOS lookup in `ios_upload`. Resolve the referenced icon names in the effective PNG/index pair, and preserve existing entry metadata and rendered crops when adding frames.
- Audit effective Android/iOS pairs across enabled active edges, legacy iOS archives and the current registered IPA. An active-only scan can misreport already supplied iOS assets as missing. Conversely, an existing iOS payload with valid slots/dimensions/mips can still be stale: compare its source PNG at the supplying archive's point with the current winning source bytes; a later version alone does not prove a change. Keep missing, stale and unverifiable provenance separate.
- Run `tools/fantasy-gauntlet-mod-tools/wf_ios_resource_audit.py --server-root <root> --report <report.json>` for this effective-chain check; `--overlay <ZIP>` checks a candidate without activating it. The focused regressions include legacy coverage, changed versus identical source bytes, special cut-in names, missing pairs and an Android-payload copy rejected as iOS. The 1.4.351 archive/readback evidence is under `assets/asset-patch/audit/ios-resource-closure-1.4.351/`; this is offline resource coverage, not device or cloud acceptance.
- For platform-specific skill cut-ins, produce a real iOS payload independently from the same source PNG, using the established iOS ETC2 RGBA slot-3 encoder. Never copy/rename Android ATF bytes into an iOS path or claim equal filenames prove platform compatibility.
- On this user's local machine, default to **4 parallel worker processes** for CPU-bound batches of independently encodable iOS platform textures, including the ETC2 cut-in flow used in the 90-cutin recovery. Use `ProcessPoolExecutor(max_workers=4)` for the Python encoder; do not replace it with threads or automatically use all logical CPUs. Reduce concurrency only for an observed resource limit and explain the adjustment; a higher count requires the user's choice.
- Keep jobs independent: each worker receives immutable per-resource inputs, generates and validates one iOS payload, and returns its result. A cut-in job receives both the source PNG and Android reference bytes for pair validation. Collect results in deterministic order and let the parent write archives/manifests, avoiding concurrent writes to shared output files.
- The existing `wf_atf` functions `build_cutin_atf_ios`, `deflate`, and `validate_cutin_platform_pair` provide the conversion and byte-level checks. Preserve the expected common/medium/android/ios root and hashed logical path for each result, and account for every required platform resource before delivery.
- Validate ETC2 RGBA alpha against an independent Khronos Data Format section 22.3 vector before trusting the selected encoder: byte1 stores multiplier in the high nibble and table in the low nibble; encoders must not emit multiplier zero, while decoders must accept it. A round trip through the same implementation can hide a shared format error. Use independent specification vectors and per-mip standard decoding, not only the pair validator (which checks slots, dimensions and mip layout). The known vector `672d6db6db6db6db` must decode to sixteen alpha values of 83; the PR45 correction adds `tests/test_atf_eac_spec.py` with full selector, clamp and constant cases. Verify the selected checkout includes the correction; it is still isolated until integrated.
- Bind each result's logical hash, source PNG and Android reference to the actual winning archive members in the enabled chain; compare archive/member hashes and decoded source pixels, not receipt snapshots alone. Existing iOS bytes can still be stale even when platform structure passes. Repair known old encoder outputs only with explicit provenance; swapped-nibble streams cannot safely be auto-detected. See the verified local case（历史本地记录） and the source/resource receipts in that task. Native device acceptance remains separate.
- Four workers change throughput only; they do not relax source provenance, per-pair validation, output counts, archive readback, or the `.cdn` write prohibition.

## Item display dimensions depend on the reader

- The Five Boss .110 device test showed two opposite failures: 20px material-bar frames rendered too small, while a weapon enlarged to 40px on a 41px canvas overflowed its detail frame. Existing donor dimensions alone do not establish the native UI contract.
- `DropItemContentsView` uses the preloaded `smallVectorIconId` frame at native size. To match this bar's 40px icons, create an independent 40x40 nearest-neighbor image in `item_icon`, preload its exact name, and change only the small-icon column. Keep the separate item/shop thumbnail at 20x20.
- `ItemThumbnailView.textureLoadCompleted` applies scale 6 inside a 168px frame: 20px becomes 120px, while 40px becomes 240px and overflows. Do not pre-enlarge weapon thumbnails to match an old standalone PNG canvas. Validate the complete `trimmed_image` frame `0,0,20,20` for standalone weapon paths; this preserves safe subtexture lifetime and alignment without alpha-bound cropping.
- Validate actual frame/PNG dimensions, effective references, rendered bounds after native scaling, and atlas pixels. Strict PNG signatures and successful downloads alone are insufficient. `tools/lens-integration/five_boss_art_contract.py` and its sparse-fixture regression reject the .110 preimage, oversized weapons, missing frames, and regeneration that would restore old sizes. No desktop AIR run is required for these checks.
- Use dedicated version variables in publishers and validate contiguous semantic-version dependencies before activation. The .110 publisher accidentally wrote an atlas-loop value into `depends_on`; .111 corrected the metadata without rewriting the old ZIP and added a regression.

## Character UI PNG roots are selected by the native reader

- `FileReader.isScaledAsset` classifies `character/*/ui/*.png` as scaled images, except `skill_cutin_*`. These PNGs are read from `medium_upload` at scale 1 or `small_upload` at scale 0.7. Common `upload` files with the same logical path do not satisfy this lookup. Missing images may silently display the native blank placeholder instead of a decoder error. This includes portraits, square icons, party/battle thumbnails and the illustration-settings atlas PNG; its `.atlas.amf3.deflate` remains common.
- Validate `(root, logical path)` pairs against the current reader, not only logical filenames or successful GETs against an arbitrary root. Keep approved medium pixels unchanged; generate the small image at the native 0.7 ratio. Platform cut-ins still require independent Android/iOS ATF pairs.
- Regression evidence: the 1.4.116 character package had all logical image names but placed 23 scaled PNGs only in `upload`; both illustration forms and thumbnails appeared blank. The 1.4.117 repair supplies both native image roots. `wf_character_storage.py` and its regression reject this exact common-only coverage pattern; stage-39 candidate publication also applies the root gate. This is resource/root validation, not device UI acceptance.

## Handoff boundaries

- Keep client resource changes separate from server data fixes in the delivery inventory. A CDN resource ZIP alone cannot deploy a server-side acquisition-source filter.
- Honor the user's testing limits. Building resources and inspecting their bytes does not authorize launching the client, starting a server, or running a test suite. Label the evidence precisely and leave gameplay/UI acceptance pending when execution was not authorized.
