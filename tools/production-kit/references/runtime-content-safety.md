# Runtime content safety

Use these gates when changing ActionDSL, diagnosing battle-effect failures, or generating Deep Abyss content. They address failures where data remains parseable but the client interprets it incorrectly at runtime.

## ActionDSL edits

- Resolve the official command/event signature before editing. Record each positional parameter's semantic role, not only its broad value type.
- Declare which 1-based parameter positions the requested patch may change. Reject every undeclared positional change. Identifier parameters must remain stable unless changing that identity is the explicit task.
- Validate the complete edited DSL against official signatures, enums, and static value types, serialize it, read it back, and validate the readback again.
- AS3 constructor signatures erase generic arguments. Consult the current SWF's `TypePackerResource2` for `Array<T>`, `Option<T>` and abstract aliases when constructing new parameters. `ShowEffect` p12 and `CreateHitArea` p15 are `Option<SLvValue>`: a fixed scale is `Some([{min:9,max:9}])`, not `Some(9)`. The latter passed the old shallow Option check but raised F1034 in `DataConcreter.concreteArray`. Skill preview can preload a leader's PF DSL, so malformed PF can also break active-skill preview. Validate all reachable skills/PF scripts together and retain the malformed scalar-option regression.
- A value being an integer or number is insufficient evidence. For example, changing an object-ID integer while intending to change a ratio remains a semantic failure.
- For player-member skills and PF actions, the native resolver binds `-17` to the executing Member and `-18` to its physical Ball. BallImpl throws in `isConditionOwnable/isBreakableBlock` and `matchCondition`; never use it for CreateCondition, ConditionalsConditionExist or ExtendCondition. Member conditions route flying/piercing to the shared squad slot. Retain Ball targets for ShowEffect following and NotifyPowerflipEnd. Run the opt-in `wf_dsl_subjects.validate_player_action_subjects` gate alongside type validation, and check the actual executor before applying this rule to other action kinds. Preserve the former skill/PF crash regressions.
- Do not treat CreateCondition's invisible flag as a cosmetic icon switch. In the verified native ConditionSlot implementation, condition queries, accumulation counts, cancellation selection and extension omit the invisible slot. Hidden marker/payload watchdogs and PF extension-budget counters therefore require explicit runtime-semantic proof; native schema validation alone cannot establish their behavior. Do not silently change an accepted icon scheme to work around this limitation.

- For character actions on the author-enabled client, use the current native-trigger → 629 → explicit ActionDSL damage-classification path. The retired GenericDamage path protocol is historical. Treat trigger, attack owner, damage class/PF level, cooldown and event notifications separately; PF-class damage does not itself prove a native PF activation. Read the [verified character integration lessons](../../../docs/development/MOD-CHARACTER-PRODUCTION-RETROSPECTIVE-20260922.md#author-integration-20260924) for reference scanning before hook removal, retained Inaho visuals/preloads, and the Android-only direct-hit/PF fixture evidence. Do not infer support on clients without the author implementation.

### Active-skill presentation production contract

- Start with the [maintained active-skill workflow and case directory](active-skill-workflow.md), the current character recipe and the workspace experience entry. Select reusable official evidence, tools and an applicable adopted case before new research; do not select a draft by folder name or modification time. Map only relevant prior lessons to this build's operation or acceptance artifact. Reuse matching compilers, collectors and regressions; character-specific renderers and choreography need explicit adaptation.
- Choose several official active-skill references that cover the new character's identity/theme, attack shape and support/state presentation. Inspect their actual DSL, parts/timeline, materials and representative composed frames; normal skill_ready and acquisition art cannot substitute for this. Reuse an existing adequate corpus rather than repeatedly scanning the CDN. For a style-mismatch revision, inspect the whole presentation of two relevant official examples, including low-light field support, main shape, peak transition and staged exit. Trace elementary cells through local groups, ancestor transforms and staggered shape sequences into the shared scene silhouette; reproducing one mascot and moving copies around is not the same compositional study. Make a short beat sheet showing which layer takes over from which, then render the complete new sequence at fixed playfield scale before freezing engineering. Check for uniform bright seams, necklace/ribbon patterns and competing peak silhouettes: more overlapping copies can still read as separate pieces. Keep a native subject only where it serves that larger sequence. Record the specific group, shape-change and timing decisions actually used, with observed limitations. The V6 whole-composition study（历史本地记录） and six-beat critique（历史本地记录） are examples, not an aesthetically accepted template. Native source cells alone do not certify a matching final composition. Distinguish client hard constraints, observed official conventions, project budgets and this character's artistic decisions. Do not promote an example's duration, dimensions, colors, scale or instance count into a universal official limit. See the eight official active-skill study（历史本地记录） and prior-character lesson mapping（历史本地记录） as bounded examples.
- Before authoring or replacing a native active-skill presentation, bind the current mechanical DSLs for every retained form, the reviewed character/material sources and the relevant client evidence to hashes. Distinguish the normal `skill_ready` selection, acquisition animations and new cast/effect layers; sharing visible material does not prove that the battle entry selects it. Preserve the agreed normal actions and unrelated mechanic/resource bytes.
- Derive one absolute-tick choreography from the actual event scheduler, but track attack events, control/hide deadlines and visual lifetimes as separate clocks. Multi-hit damage does not require restarting the field or the body at each hit. A field may outlive StopBall/HideCharacter; trace effect-manager/evaluator lifetime and movement ownership before claiming the entire action ends at control restoration. If damage finishes early, later visual activity must read as the released result, not a new unrepresented attack; discuss actual timing changes separately instead of hiding that conflict by slowing the preview. Trace the real battle body path: skill_ready selected during cutin and acquisition actions are not battle-cast evidence. Some official active skills use normal movement, while others HideCharacter and supply a distinct caster layer; use the applicable pattern and author one motivated windup, release and recovery. See the V7 native timing investigation（历史本地记录） and actual battle body study（历史本地记录） for bounded evidence, not aesthetic acceptance. Confirm the consumer's time units; preview milliseconds and GIF quantization are separate. Declare any allowed timing-leaf changes under the ActionDSL edit gate above. Removing the new presentation and reversing only those declared changes must recover the mechanical input; count actual damage commands rather than visual flashes or sound events.
- Review body-only and complete effects at the same anchors before finalizing. Drive previews from decoded native matrices, alpha, frame indices, layer and sampling flags; preserve the same visibility filters in stills, GIF and interactive playback. A body-only pass excludes effect instances inside the caster group too. Check the primary silhouette, impact direction, coverage, secondary brightness and normal/cast/restore continuity separately from file validity; assign an independent visual pass when available. Judge the intended theme and spectacle against the approved character personality in a fixed playfield at the actual preview scale: identify the emotional tone, main subject, supporting layers and how successive beats develop before expanding the animation. Do not infer a fierce or horror treatment solely from dark-element damage or a Halloween theme; review a native-sized material board against the character first. A reference count, more particles, larger sprites or fixing isolated defects is not evidence of visual quality. When the presentation calls for a creature or character acting, use distinct readable head/body poses rather than only scaling or rotating the same complete image. For pose transitions, visually mark the same anatomical landmark on each actual native sprite and inspect consecutive ticks around transitions and exits, not only impact keyframes; numerical anchor continuity alone cannot prove head continuity. Check facing, unintended doubled silhouettes or alpha gaps, secondary parts following the subject, and a motivated recovery. Freeze the preview/native identities before independent review so a later spec edit cannot be attached to earlier frames. Apply the [character workflow's coordinate and motion checks](character-balance-workflow.md#验证) and the scale/subject rules below. Do not move a fixed frame or double-apply clip and AB corrections to hide an anchor error. Offline replay does not prove native movement restoration or successful repeated casts.
- Trace the final DSL through the actual asset resolver and collection rules, including implicit hit/condition resources. For each selected layout, derive the parts-or-frame choice, timeline, inferred sprite-sheet pair and named atlas cells; do not invent a texture basename or infer standalone PNGs from parts image markers. In the inspected `battle/effect/skill_unique/<directory>/<layout>` fallback, the collector requests `<directory>/<directory>` for the sheet; record the matching-client rule rather than making this universal. Retain a negative case where an independently present/downloadable but differently named sheet fails closure. Apply the registered-sound checks below to every reachable timeline.
- Allocate the skill sub-budget within the frozen character scope using [character battle-atlas packing budgets](client-cdn-resource-safety.md#character-battle-atlas-packing-budgets). Set that allocation before adding large textures or extra poses, estimate packing for candidate native dimensions, and remeasure the compiled whole sheets before delivery. Separate high-resolution concept sheets from native texture sizes. When reducing native textures, adjust origins and matrix linear components consistently while retaining world translations and protected body pixels; recheck composition and detail at playfield scale. More spectacle does not waive the existing authoring bands, and a passing active subtotal cannot clear an unresolved whole-character budget. Reuse cells through matrices and repeated instances when appropriate; compare whole-sheet pixels, image types, per-type capacity, prebuilt instances and per-tick image commands together. Keep unresolved dependencies unknown rather than zero; these metrics do not establish full-scene packing or CPU/GPU performance.
- For impact, fall or bounce presentations, establish a causal event chain before adding details: approach/acceleration, a semantic contact anchor, short compression or break-up, lagging secondary parts and a finite result/exit. Use ballistic or appropriately motivated curves where that motion calls for them; periodic whole-object sway cannot stand in for all motion. Check actual bottom/head landmarks, local-to-global registration, unintended platforms or rows of repeated curls, and normal-speed continuity. Do not generalize V12 gravity, frame counts or fall behavior to beams or other characters.
- Deliver a reproducible recipe and source/output identities, the decoded stored-art/DSL readback, body/FX/full preview, dependency/sound and budget results, and a separate visual review. These may be sections of one receipt. Reuse unchanged matching evidence; refresh affected evidence after input changes. Keep offline, native-rule replay, device behavior, exact hit values, repeat-cast restoration, platform and performance results separate, and perform runtime or publication steps only within the existing authorization.

### Effect coordinates and parts scale

- Read the target client's PartsAnimationSource → PartsAnimation → Animation chain: parts.s becomes the container scale and multiplies child-matrix translation as well as pixels. In the inspected ActionEffectView, ShowEffect Some(scale) overrides the animation scale rather than multiplying parts.s; verify that consumer when comparing another client. Auto-fit independent-part boards cannot establish battlefield size, and a BICUBIC diagnostic replay cannot establish nearest-filtered native appearance. Record authored canvas pixels, local origin, world units and ShowEffect/reference-point bindings separately; a preview track scale of 1/s does not establish the game's world anchor.
- A full-field effect should use the intended Zone anchor; a caster-following effect should bind to the executing Member. Verify the actual AB reference-point creator and follow flag before choosing either. For the Vyrn 180×320, s=6 candidate, the map is ZoneCenter + 6 * (authorPosition - [90,160]); these values are a character-specific example, not engine defaults. Replay endpoint coordinates and layer placement, then verify the corresponding native scene; offline/schema success alone is insufficient.

### Status cancellation: integer enums and null hit-effect paths (F1009)

- For a stack containing `StringTools.replace -> FileReader.resolveFiles -> getOrReadTimeline -> SimpleEffect -> ImpactHitEffectManager.showImmediately/update -> EnemyImpl.update`, inspect the logical path argument before assuming a missing PNG/timeline or a corrupt download. In the inspected client, `resolveFiles` begins with `StringTools.replace(param1, "//", "/")`, before file lookup. A null upstream path therefore fails even when every named resource exists. This conclusion is specific to this stack; other F1009 stacks require their own diagnosis.
- `ImpactHitEffectManager.update` consumes queued `serial` effects. Trace their producer, including `ActionEvaluator.resolveConditionCancelHitEffect`, rather than inspecting only `ShowEffect` and normal-attack visuals. For `DCAll`, an unsupported selector leaves the local path null but still constructs `Option.Some({serial:true, paths:[null], ...})`; the eventual crash loses the original status-removal context. An asset inventory alone cannot detect this generated null.
- `DeletionalConditionKind.DCAll` takes the abstract `BuffOrDebuff` value. Its AS3/signature representation is `int`, but its legal values are **1 = both, 2 = buff only, 3 = debuff only**. Verify this contract in the matching client's `resolveConditionCancelHitEffect`, `DeletionalConditionKindTools.resolveConditionTarget`, and `BuffOrDebuff_Impl_.toSign`. Do not substitute zero-based `ConditionDirection` values or the different internal sign values returned by `toSign`. Apply equivalent domain checks to other deletion constructors only after confirming their parameter uses the same abstract type.

| Intended operation | Correct DSL selector | Demonstrated mistake |
| --- | --- | --- |
| Remove an enemy buff | `["DCAll", 2]` | `0` has no effect-path mapping and produces the null-path failure |
| Remove an ally debuff | `["DCAll", 3]` | `1` matches both buffs and debuffs and can remove a beneficial effect |

- The 1.4.116 Inaho investigation found these two mistakes in the effective `cnmod_inaho_midautumn_1` and `_2` skill ActionDSL payloads. Resolve the winning archive members through the enabled manifest chain and inspect both forms and every branch; an old generator output or audit receipt may describe different bytes. The incident was localized through static client/data tracing and checked with in-memory substitutions; it was not a device-verified repair when recorded.
- When implementing this repair, update the authoritative generator and both serialized skill payloads, preserving target bindings, removal count, cancellation scope, and unrelated skill behavior. Where the existing client already handles the correct values, deliver a new shared Android/iOS CDN resource increment; SWF modification or APK/IPA rebuilding is unnecessary for this data error. Do not mask the bad selector with a generic catch, silently skip its effect, or rewrite an already published archive.
- Add a focused regression with the real bad payload: reject `DCAll=0` despite its valid integer type, and check the intended enemy-buff/ally-debuff semantics so the legal-but-wrong `DCAll=1` also fails. Recheck after serialization and against the final archive. Device validation should cover enemies with and without buffs, allies carrying both buffs and debuffs, and repeated casts; check that the intended single status is removed and allied buffs remain. Keep static validation, generated-resource delivery, and actual device results distinct.

### Paired status application and cancellation

- Match the actual `CreateCondition` cancelable flag and discrimination key with the paired `DeleteCondition` selector. In the verified Android `ConditionSlot.chooseConditionsToCanceled`, cancelableKind is 0=cancelable only, 1=non-cancelable only, 2=both. These values are separate from the deletion target enum and from the removal count. A valid integer and successful death callback do not prove that the intended condition is removed.
- Restrict the cancellation with an explicit discrimination key when unrelated conditions share the same type. A common key for several sources is suitable only when their effects are interchangeable and one death removes exactly one corresponding contribution; otherwise preserve per-source identity. Do not change targets, magnitude, lifetime or unrelated buffs to repair a selector mismatch.
- Retain the original non-matching payload as a negative case. Validate serialized parameters and replay ordinary deaths, forced cleanup, mixed unrelated buffs and repeated waves against the matching client filter. The [candle repair contract](../../../assets/asset-patch/audit/pumpkin-candle-buff-cleanup-1.4.353/README.md) and its rebuilder cover the resource scope; the linked task evidence remains a finite method replay, not full impact-queue, multiplayer or iOS execution.

### Dynamic sound paths in native effect timelines (F1009)

- Treat every sound logical emitted by an ActionDSL effect timeline as a client resource reference. A compiler-generated path such as `sound_effect/character_studio/<character>/...` is not valid merely because the MP3 exists in the package: `AssetPathCollectionBuilder.loadDynamicSoundEffect` can dereference an unregistered path and fail with F1009 before the visible effect is shown.
- Before packaging author effects, inspect the author audio catalog and the effective client asset chain. If the supplied audio is byte-identical to an existing registered sound, rewrite the timeline to that standard logical (for example `sound_effect/unique/...` or `sound_effect/wind/...`) and omit the custom dynamic sound root. Only add a custom sound resource when the target client registration and runtime loader evidence both exist.
- Add a focused regression that parses all reachable effect timelines, rejects unregistered `character_studio` sound paths, accepts the mapped standard logicals, and checks the final archive for both the corrected timeline bytes and the absence of custom dynamic sound members. Keep this static/resource proof separate from device or client UI acceptance.

## Boss and terrain mixing

- Derive terrain requirements from the Boss's actual ActionDSL/ESDL reference closure and run the established compatibility checker for every selected Boss/terrain pair.
- Cover named positions such as `p0`, `p1`, and `p2`, funnel counts, active layers, and slot/group topology. Slot counts or historical allowlists are candidate filters, not runtime compatibility proof.
- Fail closed when evidence is missing. For an unpinned random choice, a verified native-field fallback is acceptable; an explicitly pinned incompatible pair must fail with the exact incompatibility reason.

## Boss quest covers

- Resolve a Boss-floor cover from the actual runtime Boss tuple, never from the terrain donor or copied template.
- Prefer exact Boss-ID tuple equality. Where official single/multi/tower aliases use different IDs for the same visible Boss, match only a stable visual identity that combines the official display name and model root.
- Treat `floor_host_quest` as diagnostic metadata only. It proves that a field belonged to a floor, not that the floor's image depicts the selected Boss. Reject it as final cover evidence.
- Verify that the selected quest thumbnail exists in the effective client-visible asset chain and retain static provenance. Do not call static evidence gameplay or UI verification.

## Boss damage trials (visible red bars)

- Treat a damage trial as a native Boss mechanism, not as a separately scheduled generic floor modifier. Preserve it only when the selected Boss's real state data contains one.
- Recognize the two runtime representations independently: Standard Enemy `au[form].g[state].m` is the Trial union and its `T2` is DamageCheck; General Boss uses `general_boss_state.c16`. Standard state `e` is an animation ID, not a trial kind: animation 0 can have a real damage trial. Do not scan unrelated packed `T2` values or General `next_state` kind `9`. Standard DamageCheck payload `a` is the percentage; payload `h` can supply a script threshold and must fail closed during HP scaling unless that script has an independent HP-dependency proof.
- When Boss HP changes, reverse-scale only the trial percentage against the final runtime HP, including any HP curse multiplier, so the official absolute damage threshold stays unchanged. Preserve the time window, success/failure branches, state topology, and every unrelated field.
- For a General Boss, materialize a private state routine, repoint only the selected clone's `general_boss.c42`, and preserve required `general_enemy_watch` aliases. Do not mutate a shared official routine in place.
- Fail closed if the source HP is only a proxy, the payload or state reference is malformed, the adjusted percentage leaves `(0, 100]`, or an absolute-threshold receipt cannot be proved. Record per-floor contracts; static proof is not gameplay verification.

## Regression discipline

For every demonstrated runtime failure, add a focused regression that recreates the former bad case and proves the new gate rejects or repairs it. Repairing one generated tower without strengthening the generator is incomplete.

- Match each master column's actual client parser when removing a reference. General Boss `c109` (`pre_action.path`) is a comma-separated string array: only `""` means an empty list. `"(None)"` is an Option sentinel in other columns but becomes a literal script path here, causing error 8100 for `(None).action.dsl.amf3.deflate`. Removing the last generated pre-action must serialize an empty string, preserve native scripts and `c110+`, and reject sentinel/empty members inside nonempty lists. Cover the compressed CSV readback and every affected generated Boss row before appending a repair version.

- Standard Funnel reverse references live in ESDL as well as master CSV. `bG` is `damage_share_target_boss_id`, and form `h` watches can name the original Boss ID. Renaming only a Standard Boss HP clone breaks these links without throwing a missing-asset error. Index every effective funnel/level for the identity gate. Either retain the native identity or clone the complete reachable actor/ActionDSL family under private IDs, rewriting all spawn, damage-share and watch references. Prove callback/resource closure and inverse identity replay; keep HP, trials, timers and unrelated parameters unchanged for an identity repair. General watch-table aliases alone cannot repair Standard ESDL watches.

## Deep Abyss reroll time records

- On 2026-09-12 the user explicitly requested a standing rule: every Deep Abyss reroll must also invalidate the previous tower's personal best floor times. Changing floors alone is incomplete. Preserve completion, rewards, unrelated modes and the separate endless quest.
- Generate `quest_time_revisions["rush:700099"]` using `wf_quest_time_revision.quest_time_revisions` from the final effective `rush_event_quest.orderedmap` finite floors. Publish the marker on the same authorized version edge; do not invent a random marker or confuse the CDN version number with the tower revision. Merges/consolidation must carry the winning marker. The 2026-09-12 regression was a .104 tower whose merged manifest retained only the .96 marker.
- After reroll, consolidation or manifest editing, run `python -B tools/fantasy-gauntlet-mod-tools/wf_quest_time_revision.py` from the source root. It checks actual active-archive bytes against the marker resolved by the server, permits a later metadata-only repair, and rejects stale/missing markers. Run the focused Python revision tests and `tests/abyss-best-time-revision.test.js` for behavior changes. Verify the delivered runtime manifest, not only a generator report.
- Old personal times are cleared lazily on progress reads when the revision differs; do not directly wipe player databases. A first new clear establishes the new record, later slower clears preserve it. Old in-flight battles and old-resource clients must not seed the new tower. Warn in the delivery note when previously mixed old/new times must reset together.
- Whole-server floor records, when enabled, use the same tower revision and remain server-local history, outside V1/V2 player saves. Never backfill them from unversioned/mixed personal records or reset them on ordinary in-game restart. Client-only text/art changes must not get an arbitrary new tower marker merely to force a reset.
