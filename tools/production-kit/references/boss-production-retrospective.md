# Boss 制作复盘与通用化经验

这份记录来自八岐大蛇高难 V2 的实际制作、黑屏排障、多人同步修复、CDN 调整和双端发布。它描述可复用的工程边界；单个 Boss 的数值仍以当前 profile、验收记录和用户最终设计为准。

## 先拆清楚改动层级

开始实现前先把需求拆成四层，并为每项指定唯一权威来源：

| 内容 | 首选承载层 | 需要注意 |
| --- | --- | --- |
| 血量、抗性、掉落、硬弱点时限、输出窗口等数据 | CDN/profile 或服务端规则 | 先确认字段已被当前客户端读取；数值变化不自动意味着要改 SWF |
| 阶段推进、父体/部件承伤、伤害账本、弱点完成、重置和同步 | SWF/ABC/AOT 或已存在的原生接口 | 需要在明确的命中提交和战斗 tick 边界接入，不能只改显示数据 |
| 资源、动画、图标、奖励导航 | CDN 与客户端资源表 | 资源启用会触发同步纹理读取，必须检查预加载闭包和入手方法 |
| 准入号、地址、封包、签名 | APK/IPA 与服务端准入配对 | 与 Boss 机制分开验收；改地址不等于改功能 |

不要因为任务提到“原生减伤”就把整个 Boss 任务收缩成一个减伤改动。开始前应列出 Boss 机制、CDN、Android、iOS、服务端准入和奖励交付范围，并分别登记是否需要改动。

## 血量、弱点和时序

- ActionScript `int` 的安全上限约为 2,147,483,647。二百亿或六百亿不能直接塞进一个 `int` 字段；使用分段账本、父体/部件承载值或高低位表示，并确保每个分段仍在安全范围内。
- 父体总血量、蛇头承载值、阶段阈值和转场条件必须一起核对。只把蛇头打死而不让父体达到阶段门槛，会出现“场上没有 Boss、过一会儿又重生”的空窗；补重生计时器只能掩盖问题。
- P4 的“硬弱点出现后的倒数”和“全部硬弱点击破后的输出开窗”是两个计时器。当前验收 profile 的含义是：出现后击破时限 3 秒，全部击破后的输出窗口 10 秒，关闭转场 30 帧，重置等待 60 帧，再激活/普通觉醒 180 帧。后续改值必须在报告中分别命名，不能把 3 秒改成输出窗口或把 10 秒改成出现倒数。
- 若设计只需要一次 P4 输出窗口，就使用一个 P4 段；不要自行实现四段循环、强制回血或“复活保留 P4 进度”。复活、联机同步和普通重置是不同路径，只有观察到对应路径的问题才增加状态字段。
- 增大 HP 后不要顺手清空所有抗性。P2 龙鳞元素抗性属于机制设计，应与全局抗性列、部件抗性和可驱散状态分别核对；“血量增加”不构成移除抗性的理由。
- Down 韧性、chain 眩晕和普通状态抗性分开处理。需要提高被击晕难度时优先调整原生韧性（本项目设计为 x9）；chain 眩晕若已有官方免疫能力，保留原生路径，不为达到效果私自改 chain 同步或 SWF。

## SWF/ABC 修改边界

- 不要把旧 V14 或其他历史 Boss 的整类、整段 ABC 覆盖到最新 1047 基线。这样容易带回旧方法、字段布局和 activation，表现为进入副本黑屏、C7050、F1034 或进入后短暂正常再黑屏。
- 用 owner、方法名/签名和基线方法体哈希定位；只 graft 明确需要的方法，保留 1047 的其他方法、trait、常量池前缀和类布局。回读报告必须列出预期变化的方法，且 unexpected body changes 必须为零。
- 通用方案应是 `BossMechanicsRuntime + BossAdapter + profile`：运行时处理分段 HP、目标集合、窗口、快照和唯一转场；八岐大蛇适配器只映射三头、阶段和原生状态。不要把阶段编号、五个头、弱点数量和资源路径继续硬编码成下一只 Boss 的模板。
- 伤害账本要区分命中事实、原生处理后的候选伤害、机制实际接受量和被丢弃的溢出。不要把某个 `damage` 参数未经确认就当作最终承伤，也不要让超额伤害跨封印、跨部件或跨阶段。
- 多人同步新增字段要走真实编码/解码路径，至少包含规则版本、实例代际、阶段/子状态、账本进度、目标完成位、窗口计时、权威序号和终态。不能只在现有 `params` 数组末尾追加字段，也不要为每只 Boss 增加一个永久枚举分支。

## 已确认的故障根因

- **C7050（领主战入口）**：Boss 任务行的条件枚举槽为空字符串，生成构造器按枚举读取时形状不合法。修复是将条件槽写成 `(None)` 并做序列化/反序列化回读；不要只改客户端报错提示。
- **F1034（多人进入）**：`BossMechanics` 的 `params[1]` 是 `EnemySynchronizeOwnerKind` 包装对象，旧代码把包装对象直接传给 `resolveStateGroupKeyOf`，类型不匹配。应先解包 `params[1].params[0]`，再解析状态组键；这是 SWF 方法级修复，不是单纯 CDN 数值调整。
- **黑屏或短暂进入后黑屏**：优先怀疑错误基线、整类覆盖造成的 ABC/原生布局不一致、AOT 没有对应新方法、坏 CDN 行/编码或缓存仍加载旧 SWF。排障时从已知可通关包开始，一次只引入一个候选变化，先静态回读，再按 CDN/SWF/原生三层二分；不要连续叠加多个版本后凭现象猜原因。
- **蛇头打完后空场**：核对父体 HP 承载和阶段阈值是否覆盖三个蛇头的总有效 HP；不要用延长蛇头重生时间替代父体转阶段条件。

## CDN 与资源链

- 候选包、正式 active/manifest 和运行镜像是三个状态。用户只要求候选时不要写 `active`、manifest 或运行镜像；用户明确正式发布后才同步完整链，并使用现有 8001 服务验证 HTTP 返回的 manifest 和 ZIP。
- 需要合并多次小版本时，先确定用户要求的回拨/替代范围，以该批原始基线生成一个完整替代包；不要把错误包当新基线，也不要只留下最后一个补丁而丢掉前置资源。
- orderedmap/CSV 类数据要保留预期换行和序列化格式。曾出现 CRLF 清理作为独立修复；修改后必须比较源、运行镜像、ZIP 内成员和 manifest，不能只看 Python 对象相等。
- 新掉落和新代币要同时核对结算规则、单人/多人数量池、稀有池概率、图标/图集和“入手方法”导航。奖励数据改了但导航仍指向旧源，会形成客户端看得到物品却无法进入获取入口的问题。

## Android 与 iOS 发布

- Android 内网转公网的直接输入是本批最终确认可用、已包含全部 Boss/F1034 修复的内网 APK。复制后只替换实际地址、生成新的 AIR `uniqueappversionid`、对齐并用固定证书重签；不要换回旧 `1047-gauge` 包再重新拼功能。
- 每个不同 SWF 都要新的 `uniqueappversionid`，即使准入号沿用；最终回读 APK 内 SWF、Manifest UUID、ZIP 对齐、签名证书、准入号和非目标成员。
- iOS 不能只改准入号或替换 SWF。以最新已验收 iOS IPA、原生程序和完整 ABC 为基线，把 Android 最终功能移植为 iOS ABC/AOT/native，再链接 IPA；`prepare → compile → link → verify` 四步缺一不可。
- `applySynchronizeKind` 等带闭包 activation 的原生入口要保留旧入口和 activation 布局，追加 hook 时不能移动原有帧。新增原生字段必须核对实际偏移，不能因 trait 列表追加就认为 ABI 不变；类对象静态槽同理，iOS 增量端口的字段/槽规则见 [ios-aot-slot-layout.md](ios-aot-slot-layout.md)。
- Android/iOS 同一发布批次仍使用不同准入号。准入配置、成品、SWF/ABC、签名材料和云服部署分别验收；静态 IPA 回读通过不等于真机验收。

## 交付前检查

1. 输入基线、SWF/IPA/APK 哈希和当前分支先登记；中途内容未变时复用记录，最终交付再校验一次。
2. 先用用户可测试的已知正常包验证，逐层引入 CDN、SWF、APK/IPA 和准入变化；每次记录实际 HTTP 资源版本和包身份。
3. Git 暂存只用显式路径。客户端方法可以提交，成品二进制、SWF/ABC 中间物、密钥、签名凭据和本地报告不能提交。
4. Windows 提交前运行仓库 hygiene 全树扫描，至少检查个人 IP、家目录、个人邮箱、`.env`、大二进制和密钥；真实内网地址通过环境变量传入。不要等 GitHub 失败后才发现。
