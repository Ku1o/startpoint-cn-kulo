## 服务端内容与性能

来源查询与商店列表共用期限、复刻期、共享购买键和库存计算，修复“入口有货，打开后售罄”等显示差异。已买完商品保留来源并返回零库存，避免道具购买后来源消失。修复请求同时带 `equipment_id: 0` 和有效 `item_id` 时漏查的问题。

箱池实际使用 `BoxGachaRewardType.ITEM=0`、`EQUIPMENT=1`；旧来源接口错误使用了 1 和 4。现在按箱池自身枚举建立索引，恢复普通道具及装备的箱池入口，活动开放状态仍由现有客户端按活动列表筛选。

静态主数据首次查询时建立一次“道具/装备 → 商品/箱池”索引，后续只处理对应候选；玩家购买记录每次读取一次，活动时间与玩家库存不缓存。普通商店列表也复用一次读取的购买记录，减少逐商品数据库查询。没有新增轮询、后台任务、数据库表或依赖。代价是进程中保留小型来源索引；预计查询开销下降，但未做云端负载测试，不承诺具体百分比。
