# Android / iOS 服务端接入协议

## 当前交付范围

用户要求先完成服务端，后做客户端。本轮没有修改、编译、签名或安装 APK/IPA。Android 和 iOS 共享下面的服务端规则；独立的构建 ID/密钥按允许列表维护。旧 Android r6 协议字段仍兼容，后续需要补齐自动恢复；iOS 客户端尚未实现。

不改玩家数据库、账号归属或存档格式。准入凭证不能代替账号登录会话，账号是否有效仍由既有登录校验负责。

## 初次连接

1. `POST /client-admission/challenge`，Android 示例 JSON 为 `{"protocol":1,"build":"对应构建ID","platform":"android"}`，iOS 使用 `"platform":"ios"`。为兼容 r6，可不发送 platform；如果发送则必须与服务端条目一致。平台不是校验豁免条件。
2. 成功响应 `data` 含 `challenge`、`nonce`、`expires_at`、`server_time`、`expires_in_ms`、`platform`。挑战 60 秒有效，绑定来源 IP，只允许一次证明尝试。
3. 将 64 位十六进制准入密钥解码成 32 字节，HMAC-SHA256 消息为 UTF-8 的 `SP-ADMISSION-1\n<build>\n<challenge>\n<nonce>`（实际换行，无末尾换行），结果转成小写十六进制。
4. `POST /client-admission/prove`，JSON 为 `{"challenge":"挑战ID","proof":"计算结果"}`。校验后签发凭证，保持原 v1 算法；两个平台均适用。
5. 登录/注册/恢复接口携带 `X-SP-ADMISSION`。只有现有账号接口成功返回登录 token 后，准入凭证才绑定到该账号会话。
6. 游戏 HTTP 携带 `X-SP-ADMISSION` 和 `X-SP-SESSION`；TCP 初始握手携带 `sp_admission` 和 `sp_session`。既有账号及房间检查继续执行。

## 有效期与续期

`prove` 和 `renew` 的成功 `data` 字段：

| 字段 | 含义 |
| --- | --- |
| `token` | 不透明的准入凭证；续期不更换，避免已有共斗连接凭证失效 |
| `expires_at` / `server_time` | 服务端毫秒时间戳，保留旧客户端兼容性 |
| `expires_in_ms` | 剩余毫秒数；初始值 1,800,000，即 30 分钟 |
| `renew_after_ms` | 建议提前续期的相对间隔；初始值 1,500,000，即 25 分钟 |
| `renew_grace_ms` | 已绑定账号的凭证过期后，允许专门续期的 300,000 毫秒宽限 |
| `platform` | 由允许列表确定的 Android/iOS 平台 |

成功校验且账号绑定匹配的游戏 HTTP/TCP 活动延长同一凭证至当前时刻之后 30 分钟。标题资源、未绑定请求、错误凭证、错误会话不延长。既有账号接口继续决定账号会话是否有效；准入有效不代表账号有效。

`POST /client-admission/renew`，JSON `{}`，携带相同的两个 HTTP 头。可重复调用，响应丢失后重试仍返回同一准入 token。过期但在 5 分钟宽限内的绑定凭证，只能经此接口恢复，不能直接请求游戏。未绑定凭证不享受过期宽限。

允许期限、停用、删除、平台修改和密钥轮换优先于续期规则。服务读取到撤销后，原凭证及未完成挑战失效，重新启用不会复活它们。未知凭证先重新握手；如果构建已停用，握手会返回更新提示。

## 失败恢复约定

失败响应保留 `ok:false`、`code`、`message`，新增 `action`；限流额外返回 `retry_after_ms`。游戏 HTTP 将该对象放在 `data_headers.client_admission`，保留非成功 `result_code`。TCP 初始拒绝仍使用旧协议 `[1,"CLIENT_ADMISSION_REQUIRED"]`，后续校验失败关闭连接；后续客户端应先通过 HTTP 恢复准入，再按原游戏重连流程恢复 TCP。

| `action` | 后续客户端应执行的行为 |
| --- | --- |
| `renew` | 暂停尚未执行的请求，尝试续期；失败再按返回动作处理 |
| `handshake` | 重新挑战/证明，随后调用现有账号 resume，成功后继续请求 |
| `login` | 账号绑定不匹配，恢复登录或显示登录页；不提示安装包过旧 |
| `retry` | 配置暂不可用或限流；保留账号，按照重试时间或有限退避重试 |
| `update` | 构建/证明不获准，显示服务端文字，引导去群聊取得安装包 |

旧包缺少凭证时会被拒绝。新客户端携带未知凭证（如服务器重启后的旧凭证）会收到重新握手提示，避免直接误报安装包过旧。随机挑战失效、证明无效时也可能需重新握手；客户端应限制尝试次数，不能无限循环或绕过校验。

## 客户端阶段待办（两端一起实现）

- 按 `expires_in_ms` / `renew_after_ms` 和本机单调计时器调度，计入请求耗时，避免依赖设备日期正确；后台提前续期采用单个任务，与登录/普通请求共享结果，避免并发握手。
- 短暂断网按有限退避重试；只要有效凭证尚可用，不因一次后台续期超时主动关闭共斗。明确停用/过期则按服务端结果处理。
- 回到前台或重连前先检查相对有效期，必要时续期/重新握手并 resume。不要清空账号、初始化存档或强制下载资源。
- 只在明确收到准入拒绝（服务端业务处理前拒绝）后安全恢复原请求；业务请求网络超时仍遵循游戏现有幂等和重试规则，不能盲目重放抽取、购买或结算。
- 更新提示只写去群聊取得安装包，不提供下载地址/按钮。后台恢复应尽量无感，不把网络波动显示成“版本停止支持”。
- 设备验证覆盖持续共斗超过 30 分钟、多次续期、网络短暂断开、长时间挂起、恢复登录、服务重启以及配置停用。服务重启本身必然失去旧 TCP，按原房间恢复能力重连；本功能不保证房间状态跨进程保留。

当前服务 HTTP/TCP 必须使用同一个 Node 进程的准入存储。多进程/多节点部署需要另行实现共享状态或 HTTP/TCP 同进程路由，不能直接扩容为互不共享的多个实例。
