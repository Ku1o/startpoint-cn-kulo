# 副本推荐编队的通关来源

交付目标是修复云服服务端；本机从云服拷贝的存档仅作只读验证样本。此项已纳入 [云服数据库优化与推荐编队修复方案](cloud-storage-optimization-plan.md)，目前为本地已验证实现，云服尚未应用。

`POST /quest/get_recent_other_player_party` 只返回相同关卡分类和关卡 ID 下，已持久化的实际成功通关快照。最多返回十种不同编队，按通关时保存的战力降序排列，排除查看者自己。

## 已修正的旧行为

旧读取逻辑将 `players_quest_progress.finished=1` 的玩家与其当前 `players_parties` 编队关联，作为 `legacy` 候选混入快照列表。通关标记只能证明玩家曾经通关，不能证明当前队伍实际打过该副本。玩家之后换上幻想连战武器，也会让该队伍出现在其他模式。旧候选和真实快照一起按战力排序，且没有停止使用旧候选的条件。

现已移除此查询来源。有真实记录才显示；不足十条就显示实际数量，没有记录就返回空数组。增加新通关记录后仍只读快照，不会重新使用当前编队补位。

## 写入与读取

- 成功结算时，角色、副角色、装备和魂珠三个槽位都必须明确，并与对应模式、编队组及槽位的保存数据一致，才保存快照。缺失的战斗信息不会从当前队伍猜补。固定编队关卡继续由现有结算调用方排除。
- 快照写入主库的 `quest_npc_party_pool`，按 `(quest_category, quest_id, source_player_id)` 保存该玩家在本关的最高通关战力编队。合法的新通关战力较低时，保留原先真正通关的高战力快照。
- 保存及读取都使用幻想连战模块的专属装备集合，检查武器和魂珠。其他模式的受限组合不写入、不显示；幻想连战对应关卡及其 Rush 练习关继续允许专属装备。
- 旧格式、损坏或已经不合法的快照不会显示。如果该玩家之后用合法的较低战力队伍通关，也可替换错误的高战力旧快照。
- 查询按战力、通关记录时间、来源玩家 ID 确定顺序，逐页跳过无效和重复组合，不会让第一页的旧数据挡住后面的有效记录。
- 已冻结快照不依赖玩家随后保存的编队；读取过程不修改正式数据库。

## 持久化和交付

使用现有数据库表及字段，不需要数据库结构迁移或清空历史。服务重启后继续读取同一张表；旧 `legacy` 候选本来就是查询时临时拼接，因此移除它不需要批量删除玩家数据。独立的 `quest_ai_party_pool.db` 用于协力 AI，本次不改它。

云服更新程序并重启后，新请求即可使用上述规则，无需导入本机数据库或等待全部玩家重新通关。缺少实际通关快照的历史队伍不能从通关标记准确还原，将在之后成功结算时积累。修复展示来源与推荐池数量保留策略是两个步骤；后者仍待优化方案实施，不能以清空推荐池代替程序修复。

部署需要同时更新以下源文件及各自 `out/` 对应 JS：

- `src/lib/quest/recommended-party-history.ts`
- `src/routes/api/quest.ts`

- `src/lib/mode15-optional.ts`
