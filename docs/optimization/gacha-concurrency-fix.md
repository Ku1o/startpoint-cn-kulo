# 抽卡并发性能修复（2026-09-13）

普通抽卡每轮整理已发送种子时，会把整份确认记录同步转换、序列化、校验、刷盘和备份。用户提供的云服日志显示启动时已有 81,033 条确认记录；抽卡负载升高后，事件循环利用率达到 100%，登录平均耗时升到约 13 秒。修复保留原有内存选种、确认和异常反馈逻辑，将持久化移出请求线程。

**抽卡种子持久化**

`SeedPersistence` 使用一个长期存在的工作线程维护磁盘侧状态。主线程只发送变化种子的最新状态，不在每轮抽卡时转换整个历史 Map。普通变化按约一秒合并，已有记录和稀有度不变时不产生保存；同一批写入过程中到达的新变化保留至下一批，旧回执不能覆盖新状态。完整 JSON 构造和原子写入都在工作线程执行，继续使用原有临时文件、回读校验、刷盘和备份机制。

工作线程写入失败后保留最新变化并重试，持久化屏障报告失败；线程退出后从当前内存状态恢复，并强制持久化恢复快照，防止把“新快照里已有这个值”误判为磁盘也已有。C3032/PLAY 反馈正常完成前等待保存；磁盘异常时保留原有尽力处理的反馈响应约定，同时记录错误并重试。管理标记成功响应等待保存，CN 服务正常关闭时整理剩余种子并等待写入完成。

约一秒合并窗口只涉及动画种子学习记录。强制结束进程可能丢失尚未保存的这部分观测，后续可重新学习；角色、货币、券、历史和兑换积分继续由原有 SQLite 事务持久化。种子文件名、格式和默认位置仍为现有 `assets`，不会用本地实验数据覆盖云服学习记录。`GACHA_SEED_DIR` 仅提供可显式指定的独立种子目录，测试必须在导入模块前设置它；单独设置 `DATA_DIR` 不能隔离种子文件。

**觉醒补算与监测**

深入计时发现，觉醒补算中对同一角色剧情主数据反复扫描占据较多时间。修复将不可变主数据建成前缀索引，保留原匹配顺序、主角 `1 → 10` 的映射及返回数组的独立性。没有缩小觉醒检查的角色范围，没有缓存玩家进度或跳过旧存档补修；剧情、联机和跨角色任务依赖仍按原计算器处理。

抽卡增加账号解析、抽取、动画、事务、觉醒和称号分段耗时；后台写入使用 `gacha.seed_write_worker` 单独标注。PERF 汇总另列角色/装备抽卡的请求数与实际抽数，仍按窗口汇总，不逐抽打印。工作线程计时不是主线程阻塞时间，接口总耗时也不能直接当作 CPU 占用相加。
