# 服务端运行时与持久化重构

## 目标

为 HTTP、实时多人 TCP、主数据库、辅助 worker 和定时任务建立明确的运行边界。所有主数据库写入最终通过统一的持久化入口完成；实时房间和 TCP 处理不得同步等待数据库提交。

## 当前基线

- 主服务仍由一个 CN Node 进程承载 HTTP、房间状态和 TCP 会话。
- 主数据库使用 `better-sqlite3`，启用 WAL；同一数据库仍只有一个写入者。
- 响应编码、NPC 队伍池、种子持久化、存档导出和管理清理已经使用独立 worker 或只读连接，迁移时保留其现有数据所有权。
- 多人房间已经有进程内 `EmbeddedMultiCoordinator`，因此房间状态不应被拆成逐战斗帧 RPC。
- 代码库仍有若干领域直接调用 `db.transaction()`；这些调用属于后续迁移清单，不能通过只迁移共斗来宣称完成。

## 本批第一步

- 新增 `persistence-coordinator`，为主数据库事务提供业务域、玩家串行队列和统一耗时指标。
- 共斗奖励事务、共斗事实事务、单人结算、邮件领取、任务结算、账号登录/绑定/引继、管理清理和设备注册先接入该入口，保持原有事务边界和同玩家串行语义。
- TCP 大厅的 `ChangeParty` 只先更新房间内存态并广播，partySlot 保存改为低优先级异步持久化；五重决战 continue 也增加异步 HTTP 入口，保留同步兼容函数给旧测试和内部调用方。多人房间人数上限仍为三人。
- Node 24 worker 诊断增加每个 worker 的累计 CPU 时间和采样窗口增量，同时记录主进程同一时间窗的 CPU 增量，用于验证多核心是否实际被使用。
- 仍需保留同步 API 的旧调用方通过兼容入口接入；这些调用不会伪装成异步 worker，后续需要命令化后才能真正搬离主事件循环。
- 新增可选的 SQLite checkpoint worker（`SQLITE_CHECKPOINT_WORKER=1`）；默认关闭，开启后每 5 秒执行 `PASSIVE` checkpoint，并在 WAL 达到默认 131072 帧或 512 MiB 时，以至少 60 秒间隔尝试 `TRUNCATE`，防止 WAL 只回填不回收而无限增大。阈值可通过 `SQLITE_CHECKPOINT_TRUNCATE_FRAMES`、`SQLITE_CHECKPOINT_TRUNCATE_BYTES` 和 `SQLITE_CHECKPOINT_TRUNCATE_COOLDOWN_MS` 调整；`[MEM]` 中同时记录物理 WAL 字节数、截断尝试/成功/busy 次数和截断前的 PASSIVE 帧数；开启前仍应在隔离环境确认 checkpoint 的耗时、busy 次数和 WAL 增长。
- 主服务关闭时会等待异步持久化队列 drain，再停止 checkpoint worker，避免低优先级大厅写入撞上数据库关闭。

本轮继续扩展了入口覆盖范围：五重决战（内部 `five-boss` 流程）的单人/多人 start、finish/abort、单人转多人清理、LevelNext/Finalize 证明记录、登录加载维护、排行榜定时结算、每日邮件定时派发、Raid/Rush 活动接口，以及普通单人战斗启动、角色突破/批量突破、羁绊领取、角色来源领取、星之碎片兑换、箱式抽卡执行、装备强化/批量强化/保护设置、关卡解锁、体力恢复、体力道具、EX 强化、装备分解、剧情结算、新手教程奖励、个人资料、玩家历史、支付到账、队伍组编辑、嘉年华默认队伍补全和管理面板玩家清理入口，都已标注业务域并经过持久化协调器。排行榜到期停榜仍同步完成，发奖和计划推进排入队列；活动、普通业务接口和管理面板继续保持原协议响应。

本阶段审计又补齐了容易被旧协议路径绕过的账号边界：旧版 `/tool/signup` 的默认存档与 viewer 会话创建、新版设备注册的账号/设备绑定/旧会话轮换/新会话插入、过期会话清理，以及管理面板的存档改名、存档克隆、账号备注、继承密码重置、设备备注和公告回执清理，都现在通过 `account` 或 `admin` 持久化命令完成。克隆和新设备注册的本地管理状态只在数据库事务提交后更新；重复设备注册会先在同一事务内删除旧 viewer 会话，再插入复用的 token，避免留下半完成会话。

幂等阶段先落地支付完成回调：当客户端提供 receipt 或 transaction_id 时，服务端按玩家和商品建立持久化回执，在同一 `player` 事务内检查回执、增加货币并记录结果。网络重试或进程重启后再次提交同一回执只返回原结果，不会再次增加虚拟货币；没有稳定交易标识的旧客户端仍保留原兼容路径，后续可根据实际请求格式继续收紧。

随后补齐了抽卡兑换、箱式抽卡维护和带稳定标识的邮件领取事务边界：角色/装备兑换现在在 `gacha` 持久化命令中完成积分检查、奖励、收件历史和兑换点更新，箱式抽卡的关闭/重置也不再绕过协调器直接写主库；邮件领取在客户端提供 `request_id` 时可在网络重试后重放第一次结果。协议里的 `api_count` 只是可能重置的旧序号，不作为幂等键；只有请求带有稳定的 `request_id` 时才写入 `player_operation_receipts`，重试会返回第一次的完整响应并跳过再次发奖。旧客户端不带该字段时保持原有响应语义。该表和支付回执一样属于服务器幂等账本，存档导入时保留目标侧记录，不把它们作为可迁移的玩家进度。

这仍是进程内队列，不等于 SQLite 已经搬到独立 worker。队列能避免实时回调直接同步等待写入，并提供同玩家串行和等待指标；真正把 SQLite 执行移出主事件循环，必须先完成剩余写入口盘点、命令化和独立连接回滚验证。

主数据库事务仍在当前进程内执行，目的是先建立可替换的调用边界并获得基线数据，不启动新的主数据库写入者。幂等阶段新增支付回执和操作回执表，由初始化器创建；两表属于目标服务器账本，存档导入不覆盖。在线存档导入与默认模板统一接受 V2，旧 V1 模板不再应用，离线迁移工具的兼容函数继续保留。

隔离故障验证已覆盖 checkpoint worker 的启动回收、长读事务导致的 `busy`、截断冷却窗口、释放读事务后的重试、错误数据库路径恢复和停止清理；同时补充了 V2 存档导入对支付及操作幂等账本的保留验证，以及 V1 被拒绝且目标数据不变的回归。Node 24 下相关测试通过，验证使用临时数据库，尚未代表云服运行实例已经部署。

## 后续迁移顺序

1. 盘点并标记所有主数据库写入口：账号、玩家、单人关卡、抽卡、商城、邮件、任务、活动、排行榜、管理和维护。
2. 将领域事务逐组改为持久化命令，保持奖励、体力、任务和结算的原子性。
3. 为持久化命令加入请求幂等键、排队、失败恢复和关闭时 drain 语义。
4. 在隔离数据库上验证 worker 连接、事务回滚、忙等待、重复请求和存档导入导出。
5. 只有所有写入口都有统一所有者后，才启用独立持久化 worker；实时 TCP 与房间状态继续由单一 owner 管理。
6. 根据 CPU、事件循环、提交队列和内存实测结果决定是否拆 API 进程或迁移 MySQL。

## 资源原则

四核机器不按“每个模块一个进程”分配。worker 数量、响应编码并发、NPC 操作和维护任务都必须有上限，并通过主进程与 worker CPU、内存、队列和事件循环指标进行调整。
