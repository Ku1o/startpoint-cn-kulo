# 服务端运行时与持久化重构

## 目标

为 HTTP、实时多人 TCP、主数据库、辅助 worker 和定时任务建立明确的运行边界。所有主数据库写入最终通过统一的持久化入口完成；实时房间和 TCP 处理不得同步等待数据库提交。

## 当前基线

- 主服务仍由一个 CN Node 进程承载 HTTP、房间状态和 TCP 会话。
- 主数据库使用 `better-sqlite3`，启用 WAL；同一数据库仍只有一个写入者。
- 响应编码、NPC 队伍池、种子持久化、存档导出和管理清理已经使用独立 worker 或只读连接，迁移时保留其现有数据所有权。
- 多人房间已经有进程内 `EmbeddedMultiCoordinator`，因此房间状态不应被拆成逐战斗帧 RPC。
- 代码库仍有若干领域直接调用 `db.transaction()`；这些调用属于后续迁移清单，不能通过只迁移共斗来宣称完成。

## 本批第一步

- 新增 `persistence-coordinator`，为主数据库事务提供业务域、玩家串行队列和统一耗时指标。
- 共斗奖励事务、共斗事实事务、单人结算、邮件领取、任务结算、账号登录/绑定/引继、管理清理和设备注册先接入该入口，保持原有事务边界和同玩家串行语义。
- TCP 大厅的 `ChangeParty` 只先更新房间内存态并广播，partySlot 保存改为低优先级异步持久化；五人共斗 continue 也增加异步 HTTP 入口，保留同步兼容函数给旧测试和内部调用方。
- Node 24 worker 诊断增加每个 worker 的累计 CPU 时间和采样窗口增量，同时记录主进程同一时间窗的 CPU 增量，用于验证多核心是否实际被使用。
- 仍需保留同步 API 的旧调用方通过兼容入口接入；这些调用不会伪装成异步 worker，后续需要命令化后才能真正搬离主事件循环。
- 新增可选的 SQLite checkpoint worker（`SQLITE_CHECKPOINT_WORKER=1`）；默认关闭，开启前应在隔离环境确认 checkpoint 的耗时、busy 次数和 WAL 增长。
- 主服务关闭时会等待异步持久化队列 drain，再停止 checkpoint worker，避免低优先级大厅写入撞上数据库关闭。

这一步暂时保持 SQLite 在当前进程内执行，目的是先建立可替换的调用边界并获得基线数据；它不改变数据库结构，也不启动新的主数据库写入者。

## 后续迁移顺序

1. 盘点并标记所有主数据库写入口：账号、玩家、单人关卡、抽卡、商城、邮件、任务、活动、排行榜、管理和维护。
2. 将领域事务逐组改为持久化命令，保持奖励、体力、任务和结算的原子性。
3. 为持久化命令加入请求幂等键、排队、失败恢复和关闭时 drain 语义。
4. 在隔离数据库上验证 worker 连接、事务回滚、忙等待、重复请求和存档导入导出。
5. 只有所有写入口都有统一所有者后，才启用独立持久化 worker；实时 TCP 与房间状态继续由单一 owner 管理。
6. 根据 CPU、事件循环、提交队列和内存实测结果决定是否拆 API 进程或迁移 MySQL。

## 资源原则

四核机器不按“每个模块一个进程”分配。worker 数量、响应编码并发、NPC 操作和维护任务都必须有上限，并通过主进程与 worker CPU、内存、队列和事件循环指标进行调整。
