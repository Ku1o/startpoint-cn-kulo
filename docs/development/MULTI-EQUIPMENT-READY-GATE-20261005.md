# 幻想装备共斗准备拦截与倒计时保护

日期：2026-10-05。实现基线：`staging@3995738e`。

2026-10-06 更新：按用户新要求，房主自身装备违规也启用 30 秒无有效操作计时，
到期仍违规则解散房间，替代此前“房主只暂停、不超时解散”的处理。

## 用户确认的范围

- 不按装备限制入房，玩家可以入房后换队。
- 非幻想关卡当前队伍携带幻想武器或魂珠时，无法准备，不弹装备提示窗口。
- 同时拦截手动准备、客户端强制准备、房主自动准备及续战开始请求。
- 违规队友连续 30 秒无有效操作后单独移出，保留房主和其他成员。
- 违规房主先暂停准备和开战，连续 30 秒无有效操作且仍违规则解散整个房间。
- 不修改客户端，不删除玩家库存或存档中的编队，不调整五重门票规则。

### 讨论过但未采用的方案

最初讨论过只允许 `PartyCategory.FANTASY=7` 保存幻想装备，禁止常规
`NORMAL=1` 及其他战斗分类保存，或者保存时自动卸下。数据层有独立分类，
但这两个方案未实施，原因是：

- 幻想 5/10/15 层仍沿用普通多人选队流程，直接禁止常规 SET 保存会影响合法幻想共斗。
- `/party/edit` 成功响应不返回修正后的完整编队；服务器静默卸装并返回成功，
  不能保证客户端缓存同步更新，后续 TCP ChangeParty 还可能再次上传原队伍。
- 只改服务端读取的分类，不足以保证客户端展示、选队和实际出战阵容一致。
- 入房前按装备拒绝也未采用，用户需要进房后再换队。

最终采用房内准备检查，不新增数据库结构，不迁移 MySQL，不增加客户端装备列表
禁选补丁，也不批量清理玩家已保存的 SET。此前 PR #21 中准备页门禁的客户端补丁源码
属于更早的工作，本轮没有将它构建成 APK/IPA 或新增客户端改动。

## 旧行为与根因

旧 `handleStartBattle()` 在整房装备预检失败时调用 `commitRoomDisband()`，
所有玩家都收到 `Disbanded` 并离房。这样能避免部分玩家先进入战斗、等待被拒绝的
队友，但把个人配装问题扩大成整房重建。

本次将检查前移到准备阶段。最后一道开战检查仍保留，但不因装备错误立即解散整个
房间；只有房主自身违规持续超时，才进入整房解散流程。

## 实现

### 共用准备判定

新增 `src/multi/room/equipment-ready.ts`：

- 沿用幻想专属物品 ID `100013..100023` 和原幻想关卡白名单。
- 同时检查当前 SET 的数据库记录和大厅实际上传的队伍。
- 兼容 TCP Option 编码及 HTTP 普通对象中的武器、魂珠字段。
- 只检查当前队伍，不因其他 SET 携带幻想装备而阻止准备。
- 发送原生 `StateChanged(connectionId, Preparation)`，同步 `isReady`、
  `yourself.state` 和大厅 roster，避免不同准备字段相互矛盾。
- 接入房主自动准备和全员准备流程，违规房主不会被队友已准备状态自动放行。
- 仅握手但尚未 Enter 的连接不触发装备踢出计时。

幻想单人及多人允许范围保持原规则。编队分类、个人展示队伍、库存物品和奖励均不变。

### 不受影响的情况

| 场景 | 本次装备规则 |
|---|---|
| 正常队伍入房后没有点击准备 | 不启动装备 30 秒超时，原有自动准备和等待回收规则保留 |
| 其他未选中的 SET 保存了幻想装备 | 不据此拒绝当前合法队伍 |
| 幻想第 5 层共斗 `300098001` | 房主和队友均允许幻想武器、魂珠 |
| 幻想第 10 层共斗 `300098002` | 房主和队友均允许幻想武器、魂珠 |
| 幻想第 15 层共斗 `300098003` | 房主和队友均允许幻想武器、魂珠 |

三个幻想多人节点由 `isMode15EquipmentAllowedQuest()` 放行，兼容关卡分类 7/8，
不触发本次装备准备拒绝、踢出或房主解散计时。铃铛、好友房和房间号进入不改变这项
装备白名单；原有层数进度和助力资格仍需满足。武器或魂珠任一违规即可命中非幻想限制，
不要求两者同时携带。

正常队友虽然不会触发自己的装备超时，但若房主自身违规并最终超时解散房间，
正常队友也会随房间解散退出。装备超时豁免不等于取消所有既有超时机制。

### 两种倒计时

**服务端开战倒计时：**

- 检查通过才发送 `StartRemainingTime`。
- 准备被拒、当前队伍发生相关变更时清除待开始标记。
- 待开始标记跟随房间实例，不使用仅按房号保留的全局集合。
- 已经显示过的倒计时不能授权开战，收到 TCP StartBattle 时仍检查队伍和准备状态。
- 合法自动续战换队保留原准备行为，违规自动换队才被回退。
- 修正队伍后重新准备，可重新进入倒计时。

这里的 `StartRemainingTime(..., 2)` 是“2 秒后开始”的协议提示。当前服务器没有据此
建立必须等待两秒的开战定时器；公开客户端对应方法主要负责显示浮字。真正开战仍由
客户端 StartBattle 请求和服务端准备检查决定，不能把它计为固定的额外两秒。

**客户端自动准备倒计时：**

公开 CN 客户端的 `MultiBattleRoomReadyCounter` 由本地计时；到期后发送 Ready。
服务器不能通过现有协议停止其显示，也不能区分相同格式的手动与自动 Ready。
本实现对每次 Ready 执行同一规则，违规时始终回传 Preparation，重复 Ready 不延长
装备超时，也不会导致房间进入战斗。

进一步核对 `MultiBattleRoomScene.gotoPartyEdit()` 与 `battleReadyButtonClicked()`：
客户端 `isForceReady=true` 时会限制换队和准备按钮，服务端的 Preparation
不会清除此本地标记。因而：

- 手动准备被拒、尚未进入强制准备状态时，玩家可正常换队后重新准备。
- 已进入强制准备的旧客户端可能需要等单独移出后，在房外换队再入房。
- 不承诺纯服务端能解锁强制准备后的按钮，也不使用假更新或断线错误掩盖这个限制。
- 真机需分别验收手动准备、60 秒自动准备及自动续战三种路径。

参考只读源码：`dennis96292/wf-2.1.125-cn-decompiled` 的
`MultiBattleRoomScene.as`、`MultiBattleRoomReadyCounter.as`、
`CooperationRoomSocketContact.as`。公开源码的部分枚举 index 与 CN 实际 wire 存在
已知差异，发包继续沿用仓库已验证的 CN index，不直接照搬公开枚举编号。

**第三人入房及编辑期间的计时（源码分析，非新增功能）：**

- 正常队伍作为第三人加入时，公开客户端的准备计时器在初始化/重置后约 60 秒触发
  强制准备，不直接继承先前两名玩家已等待的时间。
- 玩家可以提前手动准备；相关界面操作会重置本地计时，所以不是固定入房 60 秒必开战。
- 全员准备后，房主开启自动开始且条件满足时自动请求开战，否则仍需房主点击开始。
  网络请求、资源加载和队友同步另有耗时，不能承诺“固定 62 秒进入战斗”。
- 进入编队编辑并不完全暂停计时：`CharacterScene` 继承的
  `SocketConnectedSceneBase` 在编辑场景也维护准备计时器。
- `CharacterScene.viewInput()` 和 `activate()` 调用 `resetRoomReadyCounter()`。
  正常持续操作会重置本地约 60 秒；停在编辑界面不操作仍可能到期、强制返回房间。
- 本次 30 秒装备超时是另一套服务端规则，不随客户端每次点击同步重置。

上述编辑行为核对了公开客户端的 `CharacterScene.as`、
`SocketConnectedSceneBase.as`，实际累计客户端是否保留完全相同的计时细节需要真机确认。

### 30 秒无有效操作

从该玩家首次因自身装备违规被准备、自动准备或开战检查拒绝开始：

- 当前队伍发生真实主动换队或编队保存变化：重新计算 30 秒。
- 换成合法队伍：清除装备超时计时，保持可重新准备。
- 心跳、重复 Ready、重复 StartBattle、相同换队包、相同保存内容、修改其他 SET：
  不刷新计时。
- 标记为自动续战的 ChangeParty 不刷新计时。
- 点开编辑界面但不产生服务器可观察到的内容/选择变化，不视为有效操作。
- 只检查数据库与当前 wire 队伍，不在心跳上执行配装查询。

定时回调进入房间命令队列，复查房间实例、代次、当前连接和装备是否仍违规。
离房、连接替换、房间解散及战斗锁定会清理旧计时器；旧回调不能踢到下一轮或
替换后的连接。

房主和队友沿用相同的计时及有效操作定义，但到期结果不同：

- 房主自身仍违规：以 `equipment_host_idle` 原因调用现有整房解散流程。
- 队友仍违规：仅移出该队友。
- 房主装备合法、只是被违规队友阻挡开战：不启动房主解散计时。
- 解散会清除房内所有装备计时器，多个违规成员同时到期也不会重复解散。
- 到期仍复查房间实例、代次和连接身份，旧房主连接的计时器不能解散新一轮房间。

**编辑耗时的剩余风险：**玩家已经被装备规则拒绝后，进入编辑界面认真浏览但还没有
产生服务器可观察到的有效改动，30 秒仍会经过，因此可能在挑选过程中被移出；
房主则可能触发整房解散。正常队伍从未被拒绝时不会启动这项计时。
曾提出增加“有上限的编辑宽限”，但尚未实现，也没有延长当前 30 秒。不能把
“已讨论宽限”写成“编辑期间已暂停超时”；后续需验证可用的编辑状态信号再决定。

### 单独移出

仅对非房主调用装备超时移出：

- 只向违规队友发送原生离房消息；合法成员不接收 Disbanded。
- 原子释放成员映射、期待真人名单、救援状态和相应席位。
- 通知客户端后隔离旧 socket，等待其主动关闭，避免立刻 FIN 引起 C5805。
- 其他成员保留原房号，已有 AI 模式继续使用原补位流程。
- 若 AI 模式未开启，不擅自为真人房开启 AI。
- 超时离房可能显示客户端原生离房提示；“不弹窗”指准备拒绝时不弹装备提示，
  不伪造一个客户端不存在的静默踢人协议。
- 原有房间空闲回收、房主真实断线回收仍保持，不代表违规房主的房间永不回收。
- 房主装备超时解散后，全部成员会看到原生房间解散反馈；准备刚被拒绝时仍不弹窗。

### HTTP 与 TCP 交错

- HTTP `/start` 在切换为 BATTLE 前也执行整房装备与准备检查。
- 大厅当前选中的 SET 与 HTTP 请求 SET 必须一致。
- 成功开战时记录本轮已检查的选择；之后的大厅 Ready/ChangeParty/Enter 不修改
  这轮队伍。
- 已批准的同一 SET 不因随后数据库里保存了另一份配装而使队友在 HTTP start 阶段
  被突然拒绝；请求显式上传幻想装备或切换 SET 仍拒绝。
- 结算返回大厅清除本轮选择记录，下一轮重新检查。
- 保留原有 HTTP 单独调用兼容性；没有实际大厅连接的旧流程仍执行请求者数据库
  装备校验，不把仅有房间对象宣称为完整 TCP 握手验证。
- 不在已发出的战斗上强行 BATTLE -> LOBBY 回滚；恶意伪造或晚到异常请求仍使用
  原业务不可用应答，不能保证任意异常客户端都无感回房。

### 编队保存与 AI

`/party/edit` 检测当前普通 SET 的实际内容/选择变化，提交成功后通知大厅重新检查。
不禁止保存，也不在玩家保存时静默卸下装备。通知失败只记错误，不能把已提交的保存
伪装为失败；下一次准备/开战继续校验。

AI 队伍属于服务器生成状态，因此在发布 COM 队伍前，只去除非幻想房间 AI 中的
幻想武器/魂珠引用，保留角色和普通装备；不改动来源玩家库存或编队。
这样避免 AI 从历史队伍池或房主兜底队伍复制受限装备。

## 验证

可复现命令：

```bash
npm run test:multiplayer-connectivity
npm run test:multicore
npm run test:server-logs
npm run check:out -- --worktree
git diff --check
```

重点覆盖：

- 房主、队友、多人同时违规、两人房以及队友先发送 StartBattle。
- 28 项准备/倒计时/计时器专项，3 项真实 HTTP 与 SQLite 专项。
- 当前队伍非法保存、重复保存、其他 SET、合法修正。
- 已发送倒计时后违规换队、自动换队不续期、合法自动续战保持准备。
- HTTP 先到不会创建部分玩家 active quest，修正后只进入一个 battle generation。
- 幻想放行、AI 专属装备过滤、连接替换和代次变化、房间销毁后计时器清理。

测试均通过项目隔离运行器执行，只在项目 `tmp/` 中创建临时数据库和文件，
模拟时钟验证 30 秒，不修改线上存档。记录最终结果时应区分模拟协议测试与真机验收；
本轮没有构建或安装客户端，也未在云服部署。
