# 角色觉醒案例与故障经验

本页归纳历史设计、失败机制和当时的验证范围。旧运行镜像、临时回滚包、账号现场数据和过程日志不作为恢复输入；当前入口见[觉醒流程](awakening-workflow.md)。静态源码、API/自动化、设备表现和云服状态分别判断，历史通过不证明当前整批设备验收完成。

## 早期夏日莉莉丝原型：已撤回

2026-08 的早期原型针对 `151045 / resistance_princess_smr21`：未觉醒采用官方设计，觉醒后切换能力 2、3、6、队长技与主动技第三形态，能力 1、4、5 保持原样。能力 6 位于二板；任务采用编入目标角色通关任意关卡 1/3/5 次，立绘沿用进化图。

当时完成过资源回放、节点与进化等级持久化、已学习/后学习节点联动、双平台链检查，以及入口和最终面板的设备确认。这只是单个原型的证据，不能推出所有角色采用相同槽位或界面布局。

该早期原型及实验状态后来撤回。独立保留的通用修正是：觉醒技能进化节点后持久化角色进化等级，并允许重复请求零消耗补写旧存档缺失的派生等级。它使用官方角色 `341005` 的一板结构回归，不以原型的特殊能力槽作为通用依据。

早期原型撤回不等于后续同 ID 的九角色平衡迁移被撤回，也不表示当前任务扩展入口不存在。

### 活动入口隐藏的时间故障

一次故障中，活动窗口从 2026-08-28 开始，而运行环境恢复到约 2025-07-24，导致觉醒入口隐藏。修正窗口并递增资源版本后，入口恢复。可复用结论是比较实际游戏时间与双端任务窗口；不能固定套用当时的系统日期、旧时间偏移或某个长期日期区间。

### 固定四项界面限制

原生觉醒页按一板显示能力 1、2、3 和技能觉醒。队长技、二板能力 6 或未变化能力的展示标签可能与设计差异不完全对应。面板正确、标签正确和战斗效果正确是不同检查对象。

## 二板兼容故障的演进

以下故障解释为何最终方案同时要求节点、板标志、查询表和完整加载一致。早期修正的局部成功不等于后续条件已解决。

| 现象 | 原因 | 最终保留的处理 |
| --- | --- | --- |
| 觉醒后仍出现“确认学习”，再次学习返回 H400 | 服务端将已学习节点的安全重放当成非法请求；客户端状态刷新不完整 | 重复请求返回权威已学习状态、零重复扣费；真正新节点仍正常校验和扣费 |
| 已满二板重新显示可升级 | 公共响应默认值覆盖了实际 `mana_board_index` 或羁绊状态 | 学习、觉醒及幂等响应保持真实板位与完整 `bond_token_list` |
| 觉醒 +5 又指向较低的普通强化 | 整板展示模式与局部节点觉醒等级混用 | 未满板保持普通；满足条件后整板节点原子提升，完整加载修复旧局部状态 |
| `C8601`，`get_awakeValues()` 缺少 key 5 | 官方 `mana_node_awake` 缺少扩展所需能力槽 5、6 | 补齐目标稀有度和底座的查询键，核对两平台终点及服务端 JSON |
| `F1009`，`ManaBoardAwakeBulkResolver` 解析失败 | 增量响应更新了板标志，但客户端忽略随附节点列表；四槽容器又无法处理矛盾状态下的槽 5/6 | 数据库仍原子更新，增量响应延后扩展板标志，到下一次完整 `/load` 一起初始化 |

### H400 与进度保护

重放不能重复插入或扣费，也不能提前授予未学习节点。响应应覆盖该角色完整且仅包含已学习的权威节点。板位、羁绊和节点数量要同时保留；一次客户端显示倒退不能仅凭截图判定真实存档已丢失。

### C8601：查询键补充

历史 `1.4.94 → 1.4.95` 只补充 `mana_node_awake` 表：为稀有度 1～5 增加槽 5、6；槽 5 复用槽 2 素材档，槽 6 复用槽 3，低星缺槽 3 时使用槽 2。原有槽 1～4 行保持不变，并完成双平台链、CRC、服务端表同源及角色成长不变检查。

这是特定客户端表结构的修复配方；新的客户端或角色布局必须重新核对查询方式和素材档，不能按槽号机械复制。

### F1009：节点与板标志的发布顺序

查询表补齐后仍出现 F1009，说明它不是同一个缺键故障。实际存档中的节点、进化等级、板位与羁绊可以全部正确，但客户端局部缓存仍停在旧节点等级。

当时定位的 1.8.1 公共增量解析器应用角色板标志而忽略额外节点列表。单纯“多返回完整节点”不足以修正客户端。最终方案由服务端延迟增量响应中的扩展板标志；下一次完整加载同时提供角色和节点，才发布最终板状态。

当时的自动化覆盖数据库整板更新、增量标志隐藏和完整加载收敛。设备验证仍需确认重登前后不会报错或倒退；本页不把旧本地同步、提交或自动化记录当作当前云服部署和设备通过证明。

## 新案例应留下的最小证据

- 官方参照、目标角色、实际板布局及变化能力槽；是否需要进化形态、扩展板或独立立绘。
- 目标数据选择、任务/奖励、有效时间和受影响平台资源链。
- 学习、觉醒、重复请求、旧状态修复后的节点、等级、板位、羁绊与消耗。
- 对二板设计，记录查询键、增量响应、完整加载及设备重登前后的相互一致性。
- 分别记录离线/API、设备表现和云服状态；只把有来源且适用范围明确的结果提升为复用方法。
