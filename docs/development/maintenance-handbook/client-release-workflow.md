
# StarPoint CN 客户端校验与打包

## 入口与范围

Android/iOS 独立管理准入编号，不要求两端编号相同；同一正式版本的两端均须使用各自对应的新号。校验号用于服务端允许列表，不能用 APK 文件哈希、签名证书指纹、AIR UUID、资源版本号或临时会话 token 代替。

使用本任务已加载的源仓库和 `client-patch/AGENTS.md` 规则；尚未加载时再读。选择输入时读取对应平台 accepted registry、相关基线说明和本地成品台账，调用既有验证器；只有接口/输入契约改变、出现失败或需要修改验证器时才重读其实现。源仓库及本地 8001 运行源为 `<repo>`；旧兼容镜像 `旧兼容镜像` 已退役，不再作为源码、运行或客户端资源入口。保留当前已确认可用成品的累计功能；历史旧包不能替代本次确认的输入。


基线登记区分 `user_accepted`（人工确认的设备验收）与 `accepted_offline`（仅离线校验）。登记必须绑定实际安装包、平台变体与证据范围，不能把离线检查写成设备验证。

首次确认准入能力、实际改变协议/准入配对，或遇到兼容故障时，核对仓库 `client-patch/client-admission/README.md`、`SERVER-PROTOCOL.md`、`src/lib/client-admission.ts` 和相关发布记录。仅改资源、功能或同版本地址且准入输入未变时，复用本任务已确认的协议与配对证据，不重新通读协议实现或执行整套准入场景；最终载荷中的平台、编号和配对仍须核对。文档不能证明云服已部署或编号已生效，没有准入实现的包也不能只填编号就声称支持校验。

## 按平台与转换方向选择输入（本地经验）

公网与内网是同一功能版本的两个部署目标。转换方向决定直接输入，不能把“从已验收公网包制作内网包”扩大成所有 Android 制作任务都必须回到旧公网基线。

2026-10-04 起：公网客户端（Android APK、iOS IPA 及其内置初始地址、云服 `.env`）统一指向新公网 `124.222.203.221`，内网版本继续使用 `<LAN_HOST>`；旧公网 `175.178.160.158` 仅作历史输入，不再制作或分发指向它的公网包。转换仍只替换实际载荷中的地址、更新缓存身份并重签，不因改地址重复推进校验号。iOS 迁移用 `client-patch/ios-public-migration/{build,verify}_public_ipa.py`，回读须确认全包无旧地址、构造器 origin 为新地址、AOT 摘要与新完整 ABC 一致。

| 任务 | 直接输入 | 制作范围 |
| --- | --- | --- |
| 当前内网 APK 已测试正常，转换为公网 APK | 本批最终确认可用、包含最终功能及修复的内网 APK | 保留原件，从副本替换实际联网地址，更新 AIR 缓存身份并用原证书重签；直接保留现有游戏方法和资源 |
| 已验收公网 APK 转成同功能内网 APK | 当前已验收公网 APK | 切换约定内网地址，更新 AIR 缓存身份并重签，保留累计功能 |
| iOS 尚未包含本批改动，补做对应 IPA | iOS 自身最新已验收 IPA、原生程序与完整 ABC | 以 Android 最终可用版本为功能对照，移植 iOS 尚缺的最终改动，完成 AOT/SWF 配套和封包 |

**Android 内网转公网直接转换成品。** 不从项目起点、旧公网包或早期内网包重新拼装 Boss 机制及已修复方法。例如，当前可用的 Boss 适配与 F1034 修复内网包，不能换回最初只有回槽修复的 `1047-gauge` 包。只改地址时，SWF 只改相关地址常量，不重新编译游戏类；回读启动前置请求与游戏请求的地址，验证全部游戏方法、trait 和非目标 APK 成员保持。SWF 变化仍须同步更新 Manifest 与 DEX 缓存身份、核对固定包身份、原签名和 ZIP 对齐。

**iOS 从自身验收基线接续。** 提取 Android 最终版本相对其功能基线的有效改动，将 iOS 缺少的部分移植到已验收 IPA；不从历史最早 IPA 重做全部累计功能，也不重放已废弃的诊断和失败版本。Android APK/SWF 是功能与方法对照，不能替代 iOS 的 IPA、原生程序或完整 ABC 基线。涉及原生执行的方法须完成 AOT 移植，不能只替换 SWF 就宣称功能齐全；保留既有 iOS 专属行为与字段布局。

确认“目前正在使用的包”时，以本次明确确认的成品及其构建链定位精确路径和哈希，不能仅按文件名、修改时间或旧登记猜测。验收登记可能尚未记录当前内网迭代；已能从当前确认和构建报告锁定输入时，记录该输入及验证范围，不因登记滞后退回旧包，也不绕过哈希保护或擅自改写验收状态。输入完整校验一次后复用记录，最终交付再校验成品。

转换地址与推进准入号分别判断。仅做同版本地址转换、且已明确沿用准入材料时，保留实际载荷中的号与密钥；正式发布的新号或补做 iOS 的平台号按下节及本批已有发布记录处理。不要仅因重签或转换 IP 再次分配号码，也不要把制作经验更新当成恢复已暂停构建、修改准入配置或部署的授权。

## 校验号生命周期

| 制作阶段 | 必须使用的校验号 | 配套行为 |
| --- | --- | --- |
| Android 内网开发与反复测试 | 对应前一正式版本仍被允许的校验号及匹配准入材料 | 只连接约定本地测试服；不得每次测试都推进正式号 |
| 内网确认无问题后制作新正式公网 APK | 新正式校验号 | 写入真实运行载荷，准备新号的云服允许配置和所需文件，提醒用户推进情况 |
| 与该正式 APK 同版本的 IPA | 为同一发布批次配置的 iOS 新正式校验号 | 明确平台为 iOS；不能因为缺少真机测试条件继续带旧号或豁免校验 |
| 同一正式版本重打包、补做 IPA | 查阅已有发布记录，沿用已确定的该版正式号 | 不仅因重新签名、改包名描述或构建时间变化就再推进一次 |

默认按平台分别管理校验号与匹配的准入材料，例如同一发布批次使用 `android-<release>` 和 `ios-<release>` 两个不同 ID。共用发布批次便于管理，不等于共用校验号或密钥。记录“发布批次 → Android 校验号/APK 哈希 → iOS 校验号/IPA 哈希”的对应关系，并核对实际运行载荷中的号，不能仅修改包名或显示名称。

若稍后补做同一正式版本的 IPA，使用已为该批次准备的 iOS 新号；尚未准备则为该批次分配 iOS 新号，并交付追加允许条目的云服文件。不能继承前一正式版的 iOS 旧号，也不必为此再次推进已经发布的 Android 号。分配了号或通过协议测试不代表 IPA 已制作或真机验收。

内网测试前查清“对应前一正式版”的允许号与配对材料。若首次接入尚无可复用的正式号，建立明确的本地初始测试号并说明这一例外，不能假装历史旧包本来就有校验号，也不能擅自启用云服兼容模式。

每个不同 Android SWF 仍须分配新的 `uniqueappversionid`，即使内网测试沿用同一校验号。校验号复用不允许复用 AIR 缓存身份；保留固定包身份、签名及累计方法，按仓库要求回读验证。公网转换须核对启动前置请求和游戏请求的实际地址，不能只凭包内出现公网 IP 判定完成。

### 与当前服务端配对

2026-09-15 记录时，服务端的 `builds` 和密钥按单个 `id` 索引，配置拒绝重复 `id`，每条仅支持一个 `platform`。为 Android/iOS 使用不同 ID 即可配合现有结构，无需为了同版本而重构成跨平台同号。

准入结构或协议变化时核对当前实现，按下文“验证与测试协调”选择场景；新 ID/密钥或平台配对变化时验证本批新条目，不因只制作一端而重复验证未变化的另一端。平台身份、密钥匹配、撤销隔离和旧协议兼容仍是必须保持的契约，不让 IPA 伪报 Android。仅写 skill 时不修改正在测试的服务。

## 校验号推进时的提醒与云服文件

### 云服整合包默认增量范围

上一个正式交付包默认已覆盖云服，下一个包只交付其后的本批变更。只有明确要求包含上一个包或指定历史范围时才累计；旧 PENDING 记录和未获覆盖确认不再触发自动合并。此规则替代早期仓库和技能中自动合并旧待部署包的要求。范围与成品记录保存于 `<workspace>/.codex/starpoint-cloud-delivery.json`，默认覆盖前提不冒充云端实测。

同批纠错、补漏、重打包沿用该批原始基线并完整替代该批旧交付，不把错误包当新基线。共享 manifest、本批确需交付的完整准入配对及本次变化文件继续包含必要累计内容；无需再次装入云服已有的旧分包，也不得删除那些分包。

用户已明确要求：以后推进校验号时，主动提醒，并准备可替换云服的相关文件。这是该次校验号推进所必需的本地配套交付授权，无需再次询问“是否要准备”；不是自动上传、覆盖、重启云服或提交 Git 的授权。

### 本地维护完整配置，用户直接覆盖

本节只在本批实际推进准入号、变更名单/期限/密钥，或明确要求首次部署、修复或重新交付准入配置时适用。普通服务端性能、日志、功能或数据更新没有准入变更时，包内排除准入名单、密钥及 rollout/激活状态，沿用云服现有配置。即使重打 APK/IPA，若复用既有准入配置，也不自动重复交付；“需要交付时提供完整配对”不等于“每个服务器包都必须携带配对”。

用户于 2026-09-15 进一步明确：由 Codex 在本地记录并维护完整名单和配对材料，每次交付可以直接覆盖的完整文件；不要把合并工作交给用户。此选择替代早期交付说明中要求用户常规手动运行 `merge-policy.cjs` 的步骤。

- 持久主记录位于 `<workspace>/.codex/secrets/starpoint-client-admission/`：`config/client-admission.json`、`config/client-admission.keys.json` 是最新完整配对，`registry.json` 记录版本、成品哈希、配置身份、交付和部署确认状态；历史快照放同目录 `releases/`。目录保持当前用户、SYSTEM、Administrators 的受限 ACL，不放 Git 或临时清理目录。
- 准入配置确需变更时，从该主记录修改本批涉及的条目，由 Codex 内部完成合并，保留其他平台和仍允许的旧号、密钥、提示、期限及 enforce。新材料完整且配对验证通过后，先保存旧快照，再更新主记录，输出一套完整 `config/` 文件夹供用户覆盖。不得以仅新增一端的候选覆盖主记录。
- 常规交付直接告诉用户覆盖目标和是否重启；不再要求用户手动合并、反复提供旧配置，或仅因未读取实际云服就把已有完整主记录标为不可交付。用户如果手动改了云服名单，应将变更同步回本地主记录；仅在有证据显示记录缺失、漂移或冲突时补查必要差异，由 Codex处理。

## 验证与测试协调

- 提前连接未升级服务器、且改动涉及材料筛选/上限/养成窗口时，用旧服有效master覆盖普通角色满阶、超限角色及材料缺定义/库存0等不同组合；库存0不等于master定义缺失。材料模式与功能资格使用一致条件，缺配置不得让空列表进入仅接受固定格数的View，也不得错误消耗旧材料。实际生产窗口和调用者的约束应纳入AVM2夹具，先复现旧表故障再验证修复；只检查协议未变不能证明旧资源兼容。案例和复用入口见SP-CLIENT-002旧公网兼容修正。

- 从协作者 APK 补齐 x86 模拟器支持时，固定实际 APK 和提取树哈希，核对 AIR/ANE 平台声明、ELF 架构、JNI 导出及动态依赖；只导入所需 x86 原生和 ANE，保留当前 ARM 载荷及本批游戏修改。完整性检查不代表已测模拟器启动或性能。
- iOS 完整 ABC 也可能保留大量 AOT 返回占位和 script 占位。编译旧方法时，在独立 compiler-only 输入按既有声明恢复 owner 的 newclass 上下文，并检查所有目标原生符号实际生成；不得把上下文写进最终 runtime 或把退出0当覆盖通过。跨 ABC 的参数名和可选常量按语义比较，不能比较池索引。链接核对旧 flags/activation 前缀、实际共享入口及重定位；未知入口或符号不得用语义未经证明的近似函数代替。案例与工具入口见 SP-CLIENT-002 的 PR 方法移植记录。

- iOS 既有类新增实例方法时，必须比较完整继承派发槽与保留原生调用的参数约定；旧 trait 前缀保持不足以保护后代。迁出独立 static helper 时，显式传 receiver，先建立 helper-class scope 再保留原 receiver scope，并核 locals、getscopeobject、闭包/activation、全部调用和后代重写；同步重编受布局影响的累计 AOT 调用者，保留既有 wrapper 链。展开表容量不足时先核实际尾部代码和已发生的 EH 搬迁，不覆盖旧代码、不删旧边界、不使用超规格页。门禁、真实 AIR 反例及标准页共享配方从 SP-CLIENT-002 的继承派发修复入口读取；离线通过仍待目标 iOS 设备验证。

- Android差分未变化的callee仍可能是iOS缺项。整方法移植后，按真实receiver/QName核对必需callee在iOS的声明、实际实现和参数合同；叶类尾追加须先证明无子类、全旧槽不动及原native调用仍能运行时查找。新getter依赖保留的旧native时，独立回读其实际ClassTraits/MethodEnv与参数、返回寄存器，不能只看零警告或用旧返回桩代替实现。SDK解析器先用真实小声明预检versioned Multiname/early disp ID，再执行整IPA检查；限定实例见SP-CLIENT-002的战斗缺失callee修复入口。

- 客户端性能改动保留更改前的验收版本作对照，按同条件分别检查正确性、加载完成耗时与主线程连续占用；只比已有回归的新版本更快，不能说明恢复旧版性能。受控方法吞吐不等于完整加载或设备帧率，保留调度保护的收益也须实测。出现明确退化而收益尚未证实时，把撤回相关改动列入候选，不默认继续保留整套优化框架；只有已验证必要的部分才逐项回补。

## 内置 Flatomo 标签资源修复经验

遇到窄型难度条“有框但没有字”时，先区分文字来源和资源载体：救援铃铛难度标签的字形不是 SWF 文本字段，而是 Flatomo PartsAnimation `battle/common/attention/hud_attention_label.parts.amf3.deflate` 的时间轴内容；SWF 只选择并播放对应帧，第 6 帧使用 `chokyu_plus`。因此只改 SWF 选择逻辑或难度数据不会补出缺失字形。

APK 内置 `assets/bundle.zip` 与 CDN 增量是两条独立载体。当前 APK 使用内置 bundle 时，CDN 内容正确不能证明 APK 已读取 CDN；排查时记录实际读取路径和字节哈希，不能把问题归结为资源未下载。修改内置 bundle 后必须同步更新 `assets/bundle.zip.sha1`，否则 AIR 可能继续复用旧的本地提取缓存；这属于 bundle 缓存标记失效，应与下载失败区分。

窄标签的新增字形优先复用已有三字难度标签的矩阵和间距。救援铃铛的紧凑“超级+”使用现有 `超`/`级`/`+` 矩阵位置（matrix10/matrix9/matrix11），避免沿用两字“超级”的坐标造成重叠。公网与内网共用同一份资源修改方法和客户端提交；地址、AIR `uniqueappversionid`、准入配对及签名属于封包差异，不因目标地址不同复制一份排版实现。

该类资源修复先检查 AMF3 结构 round-trip 和离线渲染，再核对 APK 内层目标资源 SHA-256、`bundle.zip.sha1` 与实际 bundle SHA-1；地址、AIR UUID、准入、zipalign、V1/V2 签名归入同一次最终包校验，不在每个资源步骤重复。实际内网客户端验收按授权执行，离线渲染不冒充游戏内验证；未测试时注明。公网 APK、IPA、CDN 增量和云服交付按实际需求另行授权。详细记录见 `<repo>/client-patch/orochi-rescue-bell-superplus/LESSONS.md`。
