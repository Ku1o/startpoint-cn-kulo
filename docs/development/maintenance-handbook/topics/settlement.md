# SP-SETTLE-001 · 结算幂等、原子性与 SQLite 容量

适用：StarPoint CN 普通单人/多人 finish、五王旧回执兼容、SQLite writer、回执保留和离线容量维护。状态：所列隔离数据库、真实 writer、限定设备及专项云服场景已验证；不覆盖全部模式、高峰或长期稳定性。

## 写线程的生产回退边界

业务写线程的注册入口存在，不代表恢复启用有收益。评估前先核对[生产 A/B 回退记录](../../RUNTIME-LOG2-FOLLOWUP-20261003.md#2026-10-04-生产-ab-修正)：旧方案开启后单位请求 CPU、主循环延迟和 RAID 结算明显变差，并出现写锁冲突错误，原“先开启 writer”建议已废止。该历史不能证明所有后续实现必然同幅回退，但在唯一写入者、持锁边界及真实混合负载未重新证明前，保持停用，不把它计入优化收益预算。SQL 语句执行 worker、checkpoint worker 与该完整业务 writer 分开核对；纯命令吞吐或单一路径功能通过不能取代这条生产反证。

## 支付身份和原子结算

- 原单人已有整体事务，故障包含事务前读取旧余额/进度以及仅内存响应缓存；诊断应找实际读写边界，不能笼统归为缺少事务。按玩家锁在 finally 释放，事务内重读余额/进度、合并进度刷新并条件消费原活动局。
- 奖励、角色 EXP、事实/任务、活动清理和响应同一事务提交；普通多人走 MULTI_SETTLE_FINISH，五王专用结算保留其契约。基础奖励提交后再写 facts 会留下半结算。提交后的房间返回/NPC 池属于派生动作，失败记日志，不撤销已持久支付。
- play_id 每玩家稳定且不复用；api_count 可跨会话重复，只作短期缓存。注册旧客户端可绑定活动 play_id；无注册且无 play_id 的协议不能永久区分重试与合法下一局。冻结快照和 body 的 play/category/quest 一致，快照只供上下文，不恢复发奖资格。
- 旧 finish 不能消费新 start，rebuilt 排队期间出现新注册则拒绝写入；旧快照补结算只能清理自身身份。旧五王专用回执先于新活动匹配检查回放。注册战斗夹具同时建立内存对象与数据库活动行，不能为旧夹具放松条件消费。

## 强化点与场地玛纳

强化点按真实writer事务新读余额及冻结选择计算：确实有点才消费并启用加倍，0点仍正常结束。严格布尔flag不作隐式转换；same-play永久回执先回放，失败整链回滚。历史安全整数负点的自然结算归零与批量修账是不同操作，须在任务记录说明；不因回执重放另修余额。

礼包容量按本次实际正增量分别检查货币；只送角色/道具时，历史超上限的其他余额不能成为拒绝条件，也不能为领取礼包削减旧余额或提高全局上限。真实新增溢出仍须整体拒绝且不消耗礼包码，晚期回执失败须回滚角色、库存及领取历史；重复领取不重复发奖。实际HTTP红绿回归见礼包修正证据（历史本地记录）。HTTP400的通用客户端提示与容量根因是不同修复层，不把改状态码等同友好提示已接通。

场地玛纳从目标客户端拾取count、续存和finish载荷核对数值域，不凭单个场景或静态敌人表给跨场收益设低cap。当前Android为非负signed-int32；HTTP预检原field/base，实际writer从原始body重算并校验当次奖励，不能信主线程预计算。基础发放之后还可能有clear/score/活动/任务的玛纳奖励；所有统计生产者须统一走有界SQL增量，全部奖励完成、回执提交前再核对累计列仍是合法非负整值。不能把历史累计统计超安全整数当成拒绝当前钱包奖励的条件。

累计玛纳与钱包分开：正常安全范围精确增加；旧超范围INTEGER/REAL整值保留原SQL值和类型，本次增量无法精确表达时只跳过统计并用合并诊断明确记录，钱包及其他奖励仍按原事务发放。不清零、夹到MAX_SAFE或将JS读出的舍入值写回。SQL CASE与钱包同一个UPDATE重查原列；邮件、卖物、任务、score和finish共用入口，满钱包仍按gross统计，重复persist不重复加。近边界大增量被跳过后，后续较小增量仍可能精确增加，不能称永久冻结。V2只给此字段增加经过验证的精确十进制/REAL往返表示，不放宽其他INTEGER；普通旧档不变，新极值表示不承诺旧程序能读。V1不携带此统计，只按窄兼容策略保留极端目的地原值。反例、SQL原值与业务/存档回归见兼容修复（历史本地记录）。

回包每个字段还要符合native解析类型：普通reward_mana与field_mana分别为int，不能无依据把它们合计限制为int；Mode15合并展示到field时，合并后的单字段须仍符合int。不要静默截断或饱和展示掩盖不合法回包。域内数值仍不证明实际拾取，完整反作弊需另有服务器事实。真实双执行器红例、回滚、输出边界及AIR依据见收尾记录（历史本地记录）。

## 每局出战名单与经验归属

普通保存队在 start 的事务内冻结角色、副位、装备和魂，随当前 active play 持久化；多人优先使用进入 BATTLE 时房间已捕获的 wire 队伍，不能把随后编辑过的 SET 当成真实出战队。finish 的领队、任务、历史和经验统一用同一份名单；经验按唯一角色集合发放，不能只修 EXP 而保留其他消费者读取伪造 party。队友由本局冻结 viewer/com 身份确定，未知结果不得扩员，缺报的原成员仍可合成；重启后房主和救援角色也须从持久事实恢复。

普通队的 3+3 结构、类型、重复身份与固定队规则分开：固定队不能套普通库存/唯一性约束，仍保留零经验和羁绊占位。推荐、调级、历史等保留 party_id 不是普通槽；没有可信开战来源的旧局只做明确局部兼容，不重读当前 SET 猜历史。装备/魂的结构与冻结不等于全部持有量准入已验。当前 active 表是一玩家一行：持久当前局、内存旧局补结算和重启后完整多人 load 回战分别验收，不能以直接 finish 通过替代后两者。实现、输入契约、真实 writer 回滚及存档边界见本轮记录（历史本地记录）。

专用入口须沿真实 start 冻结：Rush/Rogue 的活动 ID 决定保存队分类；Raid 的 party_list 顺序才是 sub_id 0/1/2，party_id 可能是跨组编号，不能直接当子队下标。三队全量绑定同一 play，finish 按 sub_id 替换名单，保留原主队经验政策；冻结三队不自动授权给十八人发经验。跨队唯一性只用于可信普通新局，不套固定队和旧 NULL 快照；回归夹具也应满足原生不能重复上阵的条件。见专用入口合同与验证（历史本地记录）。

## 五重结束后的占位与旧结果

Finalize 结束的是该成员的战斗操作，不能因共享房间仍为 BATTLE 就一概判为可恢复，也不能把 Finalize 当通关成功。持久 entry+Finalize、精确玩家/play/run/房间、未 abort/未回执共同证明可将旧 active 占位转成成员待结算标记；同事务 CAS 只删除旧 play。后来的 finish 仍走原完整成功证明和唯一回执，旧 finish/abort 的 SQL 和内存清理均不能删新 active，也不能终止还在战斗的其他成员。

owner 观察与持久 SQL 有先后差：所有已绑定且持久状态仍为 active 的旧 run 的不可恢复分支（包括房间已消失）在清理、换局或新单人入口前等原 proof barrier，再在写事务重读事实；等待期间 active 已换成另一 play 则拒绝覆盖。未解决 start claim 或未知 RPC 不能当已结束。新多人首扣还须在同一 SQL 事务检查房主当前占位，合法 guest-first 与重试不重复收费；首扣时准入不等于给房主建立跨后续自由开局的长期预留。V1/V2 导入整行保留目标成员标记，不从缺失 active 或来源存档制造旧结果资格。真实 HTTP、回滚、双进程迟到结算与存档证据见隔离修复记录（历史本地记录），未证明最初客户端崩溃原因或生产验收。

### 五重证明失败后的重放与登录保全

`BUSINESS_PENDING_BUDGET` 应先对齐主线程事件循环、实际请求应用耗时和 child/parent 通道实现。后台同步长任务会阻止父侧处理应用 ACK，实时 owner 仍继续接收 TCP，握手、proof、presence 与生命周期消息可能争用有限的未确认预算；心跳不逐包申请业务 grant，不代表所有间接业务投影均不占预算。发送回调与调用方超时均不能释放仍未知的实际结果。既有日志未记录拒绝时全部占用明细，不把具体消息构成或数量/字节维度补写成现场事实。

只重放已验证成员发出的原始不可变 proof payload，绑定原 run/member/room/sequence/instance/session；确定容量拒绝可以在后续 barrier 的新受理上下文重试，不能沿用已失败 TCP begin 的坏 grant。每成员 singleflight，先排空原 tail，再按 SceneReady、LevelNext、Finalize 顺序有限尝试，恢复任务也计入 drain。原 Finalize 因 `battle_signal_order` 确定回滚时可有限重放，父 SQL 仍须鲜读真实 LevelNext；不能只依赖“本轮刚恢复 LevelNext”的局部布尔，因为原 TCP 重传可能已经补好该行。未知结果继续等待原 confirmation，其他未分类失败不自动重发，不能造 LevelNext 或通关证明。

登录收到明确 proof=false 时隐藏旧局的回战入口，跳过 detach/orphan cleanup，保留 SQL active、内存 active、成员事实及回执；并发新 play 要鲜读，不能被旧局分支遮蔽或删除。后续证明确认后才沿原 CAS 分离待结算权益；DB 已确认 settled/aborted 的旧 run 不再补 proof，只按旧 play 清占位。owner RPC 未知与明确 false 分开处理。该恢复依赖当前进程捕获的原信号，新版不能凭空重建升级前已丢失的 payload；真实受影响账号仍需定向核账。

### 群发邮件与连续主线程阻塞

路由标为 async 不会让无 await 的逐玩家同步事务循环自动让出线程。全服邮件优先冻结本批收件人与内容，逐玩家顺序 await 现有异步事务入口，复用其真实 setImmediate、玩家队列、写 gate 和回滚；完整批次保留关闭受理责任。不要一次 Promise.all 灌入数千笔，也不要用只让微任务运行的 Promise.resolve 替代事件循环让步。正常总耗时与最大连续阻塞分别验证，不能据本地小存档发送速度承诺云端时延。

诊断时 `domain.mail.queued` 是累计写入尝试，须取前后差值；它不表示当前队列长度或成功邮件数。同步兼容事务未必经过异步执行器的 `db.commit` 埋点，后者数量较小不能反驳同步群发长块。用约4700收件人的真实路由核对中途 HTTP 进展、精确收件范围、单玩家失败隔离和关服排空；五重另验拒绝、断线、删房、重登、补证、旧 finish/new active 隔离及唯一支付。当前本地修复、完整编译和隔离证据见本轮结果（历史本地记录），生产、设备和历史账号恢复分别验收。

## 永久防重与有限响应保留

永久小账本以 (player_id, play_id) 跨 single/multi 唯一；原来只检查两个 namespace 回执的方式不能在清理后承担永久防重。完整响应保留 24 小时，账本、expiry 队列、奖励、活动消费和响应同事务，并显式共用提交时间戳。新 start 在实际事务中查终态，同 pending 重试不重复扣费或重置时钟。

新近缺响应标 corrupt，超窗标 expired；已有 null、空形状、坏 JSON 回执不触发再次支付。SQL/BUSY/关闭错误继续传播，不宽泛 catch。V1 replace 先保留并按 ledger→queue 恢复，V2 preserve-target；真实删号按 FK 级联。实现入口为 src/data/domains/battle-settlement-ledger.ts 与 src/lib/battle-receipt-retention.ts；证据见保留专项设计与验证（历史本地记录）。

大 JSON 表不在启动时全量建索引或回填。按 rowid 对所有 operation 限量后筛战斗元数据，先补 guard 与队列再清理；独立小表持久 cursor/lease，queue.created_at 与响应一致。短事务受写入 owner、shutdown admission 管理，批间 yield，失败回滚游标且不记完成。仅清 quest_finish.single/multi；专用五王、邮件、抽卡、支付及 clock abort 保留原契约。删除只释放 SQLite 内部页，小账本仍随累计局数增长，TTL 不是硬 GB 上限。

任何 prune 后不能只恢复旧 receipt-only 代码；优先暂停 retention 并保留新 guard。完整回旧版须停服恢复一致数据库，并另确认新进度损失。专项同步先比对实际 src/out 依赖，从固定提交构建精确清单，保留正式整合包基线；准备单不等于部署证据。

## 永久奖励与存档一致性

【已验证：临时 SQLite、真实 V1/V2 覆盖及管理员 HTTP 导入】新增一次性角色/物品奖励时，永久领取事实必须与奖励实体联合保护。仅把领取记录设为 portable 或与目标取并集不够：领取后导入不含奖励角色的旧档，会删掉角色却保留“已领”，造成无法再领取的永久损失。覆盖事务应在任何替换前校验来源与目标的领取事实、来源奖励实体及必要关联；按既有导入合同安全保全完整权益，或明确拒绝危险档并保持原库不变，不能清领取标记重刷、补满培养或静默只保留半套状态。含奖励实体的档按正常覆盖合同恢复，较旧培养值是否回退须明示，不把局部防丢失扩大成所有角色进度只增不减。

回归同时覆盖来源/目标已领与未领、来源有无奖励实体、旧档缺字段与新档空表、跨账号和 fresh-process 防重，并验证失败/迟到回执/导入末段错误全部回滚。拒绝危险导入应比较完整便携表与角色/库存/培养状态，不能只断言领取行还在或再次发奖返回 null。首获回包、成功条件与普通重复份也独立验收；依据见永久奖励与存档回归（历史本地记录），限本地隔离证据，不外推正式库迁移、设备或云端。

## 连战显示状态与历史称号读取

角色立绘显示状态只需 `id/evolution_level/illustration_settings`，不要为此加载完整角色、日期和羁绊记录。同一结算的主/副位可合并批查并按需复用；缓存限于本次事务，文件夹奖励等角色写入边界后失效，不能跨请求保留旧值。旧字段沿 `deserializeNumberList` 的逗号解析，SQL NULL、空串、NaN、非字符串和缺失角色的返回语义分别验收，不能套用其他展示查询的 JSON/容错解析。以真实 SQLite、旧完整 getter 和新投影对照槽位顺序、重复角色、跨玩家隔离及奖励前后状态。

普通榜关闭不等于停止成就：普通深渊每层成功可能仍检查海豹称号，未拥有者会反复读取个人历史。以保留全历史资格的单条存在性查询替代 `.all` 后逐局检查时，保留 CASE 的 NULL 语义、恰好30行、原状态/身份限制和唯一发放；不能随意截断历史、只查最近N局或仅末层检查而漏补旧称号。调用次数固定不代表数据库内部工作量恒定；已有索引按真实结构复用，不凭源码DDL推断生产缺索引；正式基准开跑前，对每个seed实际的 sqlite_schema/index_info 及原/新 EXPLAIN 作断言，不能仅凭装配代码或源码表结构声称匹配生产索引。耐久成就的当前run处理与海豹历史查询分别测量。

结算基准必须覆盖实际榜单开关：关闭时海豹检查可能每层一次，开启时可能仅末层，错配开关会改变热点频率。每个前后样本从相同且尚未获称号的seed重建，交替顺序，预热与SQL计数代理分离；比较返回值和数据库状态，保留较慢的小历史负例。明确区分目标代码、含BEGIN/COMMIT事务和完整HTTP/TCP；30层耗时之和不叫单次延迟，本机暖缓存收益不能证明生产秒级长等待已解决。实现、旧字段/奖励边界回归及配对证据见本地读取优化（历史本地记录）。
## 在线 checkpoint 和离线整理

在线启动、定时和手动 checkpoint 使用 PASSIVE；旧 truncate 环境项不得重新启用在线截断。busy_timeout 限制等待锁的时间，不限制持锁者磁盘 I/O；在线 TRUNCATE 可在同步时阻塞写入。PASSIVE 允许 WAL 复用，物理高水位不等于未回写量，长 reader 仍会延迟回写；后台 errors=0 不证明玩家结算无错，也不应降低同步持久性。

`journal_size_limit` 可以在 WAL 安全自然重置后的首次提交中回收物理高水位，但它是逐连接设置的保留目标，不是活跃 WAL 的硬上限。实现时核对主连接、writer/leaderboard 工厂、持久化 worker 和 checkpoint worker 的实际入口；重开连接需重设，不能只设置维护连接。长 reader 或大事务仍可让 WAL 超过目标。

保留目标调优用磁盘空间换取更少的缩文件次数和释放量，不能把较小目标当成更早触发回收。比较不同目标时，每个策略独立重新造出匹配的当前代 WAL、保留各自真实文件历史并交替执行顺序，避免先缩小的文件污染后一策略。1 GiB / 2 GiB 的本机多轮与真实结算对照支持较大目标减轻回收停顿，但无缩文件的复用场景没有稳定加速，后续普通批量争用仍可较长；参数采用状态及逐场景依据见保留目标对照（历史本地记录），不外推首次巨大回收或云服延迟上限。

自然回收仍会在写事务提交时执行缩文件 I/O，不能由“没有主动 TRUNCATE”推导为“不占写锁、不延迟结算”。本地 Windows/NTFS 的巨大 WAL 首次回收已验证空间与数据保全，但低延迟要求未通过；日常尺寸的多轮回收提交增量达标，仍有有效并发请求等待超出目标，两种边界应分开验收。候选实现未部署。复现时用真实 SQLite 写出高水位，分别记录 PASSIVE、线程协调、COMMIT 与并发请求最长等待；不能只看 errors=0 或 P99，少数回收请求可能落在 P99 之外。依据见首次回收记录（历史本地记录）及日常多轮与真实结算补测（历史本地记录）；本机结果不外推云服磁盘和玩家负载。

【已隔离对照，生产待验证】先检查 PASSIVE 返回 `log==checkpointed` 再做 busy0 TRUNCATE，仍不能保证只截文件而不持写锁同步：返回值针对该轮快照，TRUNCATE 取写锁后会重读最新尾部。busy0 限制抢锁重试，不限制拿锁后的 I/O；忙轮次、成功次数和实际释放必须分开。分段保留与截到零的目标不同，应比较完整策略的空间、单次窗口、写入排队与主循环，不把较少释放量的耗时差当成等字节效率；写线程模式的较低 loop 停顿也应保留，不能只选直接写入优势。相同输入下，实际回收与 HTTP 生命周期未重叠的样本不作相同锁碰撞或纯维护增量。首次大文件回收、日常截断、冷首笔与关闭清理分开，完整极值不能删；参数、每次原生区间和限定结论见分段与条件 TRUNCATE 对照（历史本地记录）。

连续复用测试必须按当前代有效帧造数，不能以保留的物理长度判定新一轮已写满；先完成账号/房间/start 准备，释放固定 reader 并 PASSIVE 完整回写后直接调用真实 finish，避免夹具额外写入提前触发重置。事务观测先核对实际入口，coordinator 的直接 transaction 不一定经过可选 probe；HTTP 总耗时和 outer callback 返回后的提交阶段应分别记录。同时发起维护与 HTTP 不等于实际缩文件期间覆盖了结算：大 PASSIVE 可能耗尽整个请求窗口，应核对真实 native COMMIT 与 HTTP 的单调时钟区间；需要补这个缺口时先完成 PASSIVE、无额外写入地并发触发，再保留原来的正常忙/延后回收结果。测试持锁协调也可能制造假延迟，原子计数等待须在同一次读取上判断终态再等待，不能在到达终值后等待已无后续通知的计数；保留受污染原始结果，仅修正并补测相关场景，不覆盖有效超标样本。

分阶段缩文件已通过实际维护 worker 的限定隔离回归及真实结算共存验证；当前主线采用及云服部署状态见主线整合回执（历史本地记录）。不要只在结算事务加动态目标：其他 autocommit 或重开的固定小目标连接仍可一次缩到底。普通在线写连接初始化为 `journal_size_limit=-1`，唯一维护连接在 PASSIVE 完整回写后以 `busy_timeout=0` 尝试 BEGIN IMMEDIATE，锁内读取并原值写回 `user_version` 形成真实小提交，在 COMMIT 前按当时文件长度选择 `max(final,size-step)`，依靠自然重置分阶段回收；不得直接操作系统截断 WAL。同值 metadata 写已实测产生自然重置，非零及有符号边界原值保全；维护连接开始写入后使用 FULL，普通业务连接的同步配置不变。维护事务仍占写锁，阶段字节数不等于毫秒上限。维护停用、长 reader 或竞争写入会延后回收，普通连接可继续复用但不能承诺自动物理缩小持续推进。维护 BEGIN 的正常 SQLITE_BUSY 必须与已成功的 PASSIVE 及真正 checkpoint_error 区分，避免误触发现有所有权切换；其他错误回滚后上报，不另加自动恢复系统。当前实现身份、实际尺寸分段、部分回收停启、自动计时器及真实 single/multi 的默认/writer 模式依据见隔离实现与验证（历史本地记录）；此前大 WAL 原型时延仅适用于独立可行性实验（历史本地记录），不能外推当前 worker 的云服表现。

【已验证：生产只读取证及隔离机制复现】PASSIVE 的 `log==checkpointed` 仅覆盖本轮起始快照；业务在回填期间追加尾部后，维护即使拿到 WRITE 也可能仍处于 READ1，随后同代际追加而不重置。正常 busy 或 errors=0 都不能证明空间回收。定位时应对齐实际连接的 CKPT→WRITE、实时帧/回填帧及代际，不能把旧 read mark 数值当作活跃旧读者，也不能把连接编号直接当线程 ID。有限窗口内大量全部无锁的时点可以排除该窗口中某条已观察连接持续占读锁，不能永久排除短读、交替读者或外部进程。实际发生过一次缩小也不等于持续负载下已稳定回到目标；现场证据见回收时序诊断（历史本地记录）。

【已隔离验证，持续收敛未通过，未采用】候选在首次完整 PASSIVE 后实际回收尝试未见重置/净减少时，同轮最多再追平一次；首次 partial、低于目标或已观察到重置则不追加。它在短窗口增加了回收机会，但延长固定写负载仍多轮忙、未到目标，不能作为稳定收敛修复直接推广；两次调用上限也不是 I/O 时长上限。为保留每轮最多一次缩小，需在持 WRITE 后、任何实际写前记录 WAL 头部代际，COMMIT 后再观察：真实缩小后业务可能在 post-stat 前扩回文件，此时净减少为零也必须停止本轮。真实文件读取错误沿现有错误路径传播，不当作“未重置”继续重试。依据见同轮追平实现与验证（历史本地记录）及该目录的竞态、原尺寸与持续负载证据；该候选未整合或部署。若需确定的回收窗口，必须重新审查写入准入与所有实际 native writer 的存活/退出边界；现有 exclusive gate 会拒绝同步直写，不能直接套用，也不能用调用者 Promise 已拒绝推断工作线程原生连接已停写。

【已隔离验证，生产待验证】较小的协调方案是后台保持重 PASSIVE，最终 PASSIVE+自然重置进入现写 gate 的同步排他回调：在 pump 中同步完成、释放 exclusive 后才 resolve Promise，不可改成 `acquire(true).then(callback)`。整个最终窗口无 await/IPC 等待，普通 main Sync/raw 写无法在调用栈间插入，因此不必仅为维护而迁移全部 Sync 调用；代价是最终 I/O 阻塞 main，并延长触发 gate 释放/ACK 的请求完成时间。真实慢 DB sync 仍可能很长，尾部小或字节上限不能保证毫秒上限；应按实际主窗口、完整请求及 loop/TCP 分别验收。主线程阶段采用更小字节预算以减少单次停顿，参数和来源留在协调回收隔离记录（历史本地记录），不能外推为云端已采用或玩家 RTT 已验收。

原生写线程的排空须以最终 SQL ACK/真实 worker exit 为准，初始化需等有效 ready/settings；caller timeout、rejectAll 或 current 指针变更都不代表 native 已结束。过期 worker 的 ACK/exit 清票据必须在 current/pending guard 前处理。维护应先进入公平 gate 队列，不能在入队前等待 native active 归零：maxInFlight>1 持续补队列时计数可能一直非零，维护将无法阻止新 shared 写入。同步回调中若仍有真实 native 活动则立即返回，不持 gate await，保留待执行请求；后续重入也不得形成 Promise 微任务自旋。用真实 coordinator+多 inFlight writer、排在维护后的 future admissions，以及 timeout 后 late ACK/exit 验证，不能只用单 active dispatcher 或 Promise 清空作证明。运行拓扑仍要求同一主库不被另一服务进程同时写入；本进程票据不构成跨进程锁。

阶段目标必须在所有业务写入及 savepoint 回退结束后、COMMIT 紧前持写锁采样。已复现开头采样后 cache spill 扩 WAL、ROLLBACK TO 回退逻辑帧却保留物理高水位，最终释放量超过步长；以“事务前尺寸减事务后尺寸”会漏掉这个反例，应核对提交前实际高水位。基准 fixture 不能假定同值普通 UPDATE 已写出锚定 WAL 代所需的新帧：本机原装配未锚定预期代，改为先执行真实值变化，再固定读取快照，并用当前代标识及 SQLite 帧数确认输入。Windows 隔离负载夹具不要用未经实测粒度的短 `Atomics.wait` 模拟业务持锁；两毫秒请求可能变成约十五毫秒，从而制造队列积压和 TCP 超时。公平对照应使用匹配 WAL 历史、固定真实事务数/到达计划及校验和，记录实际到达延迟、逻辑帧速率与阶段回收吞吐；异常旧夹具连同源码前像保留，修正后另建结果，不以更少写量或过载样本评估策略。

严格配对要在原生连接打开前核 seed 双 hash，并在业务准备后、首次计时前再次核 DB/WAL 双 hash。固定 JavaScript Date/RNG 不会固定 SQLite `datetime('now')`；已复现任务快照时间不同使 WAL 长度相等但 hash 不同。必要的准备期 SQL 时间替换只针对已定位语句，绕过其 statement 缓存，计时前恢复原 SQL、缓存函数、时钟与 RNG，并用原生语句及最终双 hash 验证；不把固定 SQL 留给业务测量。大 BLOB 压力须让所有页随序号真实变化，以实际有效帧速率描述；只改首四字节不能代表整块写量。大 WAL 的 hash 用流式读取，头部仅定长读取；不整读 GiB 文件取头。回收次数按负载原生时间窗分类，失败请求的全部等待仍保留；相应脚本与失败前像见上述条件 TRUNCATE 对照目录。

离线整理前核对历史扫描完成、last_error 为空、lease 释放。新尾部超过 cursor 时按业务键核对永久账本和队列/时间戳，不能只用 max(rowid)>cursor 判未完成。VACUUM 会重排没有 INTEGER PRIMARY KEY 表的隐藏 rowid；未完成扫描时不可直接整理，整理后不用旧 cursor/max(rowid) 计算进度。

在明确停服与维护授权下，先快照并确认进程、监听、自动拉起停止，再用独占连接和维护锁执行 TRUNCATE→VACUUM→TRUNCATE。保留原业务字段、永久账本、queue 和 retention 状态，不顺带运行包含备份/迁移/清理的广义 apply。可参考本批整理器（历史本地记录），使用前刷新目标 DB、容量、回填和停服条件。

验证比较全表行数、类型化字段摘要、逻辑结构、完整性和 FK，不把物理 rootpage/隐藏 rowid 纳入逻辑数据摘要。历史专项云服整理及首轮观察见最终回执（历史本地记录），有限单人窗口不推出多人、高峰或长期通过。

### 云端正常停启与回收归因

Windows 云服的 SSH 与现有主进程可能处在不同 Session。停服前刷新实际 PID、创建时间、账号 SID、父子关系、端口和 Session，不直接复用历史 Session 0 断言，也不以删除断言代替同会话执行。已有主进程正常关闭 handler 可通过同会话的临时 InteractiveToken 按需任务、RunEx 指定实际 Session 激活 loopback inspector，再在目标进程内核对身份及唯一 SIGINT listener 后 `process.emit('SIGINT')`；这不等于发送系统 Ctrl-C。Windows 的 `process.kill`/`child.kill` 不能替代该有序路径，旧 logger 的信号转发还可能触发较短的强杀计时器。等新 graceful-complete 日志、exit0、进程与端口退出后才覆盖，启动沿用云服既有入口；临时任务只在获准维护窗口创建，用完退役。该限定云服路径的实际停启、文件读回和初始生产观察见部署回执（历史本地记录），不外推其他登录会话或权限条件。

停服关闭最后一个 SQLite 连接可能自行清理旧 WAL，所以必须分别记录停服前、停服后、启动后三个时点，不能把正常闭库释放空间当成新在线回收成功。只读采样中，WAL 代际序号及盐值变化而物理长度保持，支持自然重置与文件复用；它不能证明超过目标后的物理缩小。上线后低于目标时保留“分阶段回收未自然触发”，继续观察真实负载，不为验收人为扩大真实库、强制 checkpoint 或删除 WAL/SHM。

### 云服只读检查的资源与退出边界

**已验证（本次生产事故与恢复）**。只读诊断也会占用生产资源；本地 SSH 客户端超时或退出，不代表远端 PowerShell/Node 已退出。出现超时先按本任务启动时间、PID、父进程和命令身份核对远端检查进程，不能继续叠加同款探测。只终止已确认属于本任务的失控只读检查，游戏进程仍走有序关闭约束；退出确认与资源恢复须分别读回，不能用发出停止命令代替。

在线日志检查固定字节区间并限制子查询时间；`Get-Content -Tail N` 只有行数约束，不提供内存或进程寿命保证，不作为本项目在线检查默认入口。性能统计应解析对应字段，启动异常匹配应限定诊断标签，不能把 `admission.total` 和 `domain.mail.failed=0` 跨字段正则匹配成错误。本次失控脚本的具体分配点未捕获，不能断言某个 cmdlet 泄漏或存在无限循环；已在任务入口禁用旧检查，改用有界 Node 日志读取和原生命令。依据：部署与检查事故回执（历史本地记录）。

## 在线完整备份与账号清理

**已验证（本地隔离，云端大库待验）**。后台清理长期没有进度时，先区分 planning、backing_up、indexing 和 deleting；备份未完成不能归因为级联删除。目标数据库文件的大小只是写入高水位，不能当完成比例。新备份仅在 `backup-info.json` 为 completed 且实际备份线程成功退出后可用于后续删除；失败/取消记录和历史完整备份分别保留，失败目录不挤占成功备份保留份数。

SQLite 分步 backup 的 native step 仍同步占用调用线程；其他连接持续写源库可令备份反复重启。在线完整备份使用专用只读 worker，`BEGIN` 后执行实际查询固定 WAL 读快照，不把复制/整库校验放在玩家请求线程。复制完先释放源快照，再检查目标完整性。版本和选档 sidecar 在启动前捕获原字节，并在固定快照内校验账号、存档和默认归属，不能在备份结束后混入较新的选档文件。长读快照延迟 WAL 回收，必须设总期限、复制停滞、WAL 增量与取消边界；目标校验阶段只受总期限/取消约束，不以缺少复制页进度误判停滞。

取消/失败不进入删除，正常关闭先发取消再等待清理 Promise。单并发槽和 drain 必须等 worker 实际 exit；completed/failed 消息及 terminate Promise 均不能替代 exit，终态消息后还应有退出看门狗。JS 取消不能即时打断正在执行的 native 磁盘 I/O，不承诺固定退出毫秒数或磁盘无竞争。

在线清理只读检查外键支持索引，缺失即拒绝并提示停服维护，不在在线任务或既有库启动时全量建索引。新建空表可随初始化建立必要索引；按需创建的登录表也须覆盖。partial index 不能证明全量覆盖；单列 `INTEGER PRIMARY KEY` rowid 别名虽无 index_list 项仍有直接定位能力，应避免误报及冗余索引，并保留 DESC/真实 PK 索引例外。即使索引齐全，单个大账号的级联删除仍可能耗时，备份修复不等于大账号在线删除已实现时间上限。

复现与回归优先用合成 WAL 库多连接持续写、固定快照内容摘要、取消/超时/停服零删除、sidecar/版本失败、成功备份保留与实际 exit 场景；响应能力使用独立进程 HTTP 客户端，不能只用同线程 inject。当前源码测试入口为 `tests/admin-database-backup-worker.test.cjs`、`tests/admin-database-backup-sidecars.test.cjs`、`tests/admin-database-backup-responsiveness.test.cjs`、`tests/admin-cleanup-backup-integration.test.cjs` 和 `tests/admin-cleanup-indexes.test.cjs`。实际范围、失败纠正与限定结果见本地修复回执（历史本地记录），本机合成库耗时不外推云端或玩家体验。

## 异常回滚与有区分度的验证

- 真实 writer 用持久 SQL trigger 或线程内 seam 注入故障；主线程 mock/TEMP trigger 不覆盖 worker 连接。最终 receipt INSERT 失败时比较余额、经验、库存、装备、任务、日计数、关卡和活动的全玩家状态；解除故障后原 play 成功一次，重复请求不再支付，覆盖排队新 start 和进程重启。
- 可选练习历史仅跳过明确类型的遥测校验错误；装备读取、程序异常、INSERT 故障必须传播并回滚，不按错误文本或宽泛 catch 跳过。zones:[null] 可能在后续任务统计仍被拒绝，须验证完整 HTTP 链。旧 MULTI_RECORD_BATTLE_FACTS 与当前 MULTI_SETTLE_FINISH 分开追踪，见相关修复（历史本地记录）。
- 深渊单/双塔 clean 预判可省空写事务；dirty 保留锁内重读、双塔外层原子事务及嵌套 savepoint，外层 catch 内部失败后继续提交也不能留下部分重置。用实际 Statement.run/db.exec 观测 BEGIN/COMMIT/savepoint，并让第二连接在 BEGIN 前提交新版本/进度检查不重复重置；省 COMMIT 不等于省 fsync 或固定毫秒收益。已有外层事务的 load/Rush 主要省内部 savepoint，见刷新方法与负对照（历史本地记录）。
- 正常关闭中已接受的写入保存，与 HTTP 回包交付分开；断网后双方各自支付，与双端同步恢复分开。正常双人单次支付、BothBoss 换场、五王失败退出、原局重入是不同验收项；详见[测试专题](testing.md)和完整历史依据（历史本地记录）。
