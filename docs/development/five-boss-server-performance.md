# 五重服务端性能收紧

本次在 0909 整合版本基础上减少同步数据库工作及重复异常诊断。客户端资源继续使用同一份 1.4.103，下载由现有 Cloudflare 部署承担。本次没有修改下载线路、Cloudflare 配置或游戏规则。

## 实现边界

- 单人 AUTO 标记通过活动任务的 player_id 定位 play_id，再以 `(player_id, play_id)` 主键更新对应单人记录。仍要求当前任务为五重单人、账本为 active、auto_used 为 0。关闭 AUTO 不清除标记，历史回执不变。
- 设置保存对请求中的游戏选项使用条件 UPSERT，值相同则不更新；忽略 `profile.*`。HTTP 设置及 AUTO 标记共享同一个事务。其他调用方的批量更新继续保留自己的事务或嵌套保存点，失败可回滚整批。
- 五重结算在当前同步调用内复用已经查到的账本；普通多人及五重生成队友关注信息时复用本次认证的玩家身份。仍执行对局身份、关卡、战斗证据与发奖幂等校验，不跨请求缓存数据库状态。
- 五重 HTTP 拒绝与 TCP 信号拒绝按玩家、对局、操作及原因合并。每个 60 秒窗口最多保留 128 个键，每键最多 1024 字符，仅首次调用读取并输出完整上下文。重复请求只累加计数；超出键上限的请求累计 overflow，不逐个建立缓存。
- 一个按需启动且 unref 的计时器输出 `[FIVE-BOSS-REPEAT]` 汇总后清空状态，无逐玩家定时器。原 `[FIVE-BOSS-REJECT]`、`[FIVE-BOSS-SIGNAL]` 首次信息保留；诊断读取或日志输出失败不替换原业务错误。

`suppressed` 表示同一键在该窗口内省略了多少条重复详情，首次详情另计。`overflow` 表示因窗口容量上限未保留独立上下文的请求数。下一窗口可重新采样详情；突发退出前的最后一段计数可能尚未汇总，首次详情已经输出。

## 验证方法与实际边界

对照基线为 `06fc91edaa7b40e3e270b78ba76e192762f5574e`。使用 `tools/bench-five-boss-concurrency.cjs`，由父进程发送真实 HTTP 请求到独立子进程，另用 TCP 回显探针测同一事件循环的响应。测试库由脚本自行创建，不读取玩家运行库。

Windows 子进程限制到一个逻辑处理器；24 路 HTTP 并发，共 960 个设置、开战、成功结算及缺证据拒绝请求。24 个单人账号各带 6000 条历史记录，另有 12 个三人房间；成功结算生成真实队友信息。包括生产使用的 MessagePack/base64 序列化。TCP 探针不是手机战斗协议验收。

将上述基线提交的以下构建文件按原路径存入独立目录，作为 `--baseline` 参数：

- `out/data/domains/option.js`
- `out/routes/api/option.js`
- `out/multi/five-boss/solo-runtime.js`
- `out/multi/five-boss/lobby-runtime.js`
- `out/multi/http/five-boss-battle.js`
- `out/multi/http/battle.js`

先执行 `npm run build`，再执行：

```text
node tools/bench-five-boss-concurrency.cjs --report <报告.json> --baseline <旧构建目录> --single-core
```

`--reverse` 可颠倒新旧运行顺序；`--history 0` 可对照无历史记录的情况。各组使用相同主数据及未修改模块，新旧进程各使用独立新库，不启动生产服务和计划任务。测试未加载 `.env`，详细游戏日志按默认设置开启。测试账号的角色和其他持久化数据远小于成熟线上账号。

2026-09-09 三轮有历史记录的结果如下，其中一轮颠倒顺序。表中数字为各轮指标的中位数，不是把请求混合后计算的总体分位数：

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 处理相同请求的进程 CPU 耗时 | 1906 ms | 1672 ms |
| TCP 探针 P95 | 74.463 ms | 68.372 ms |
| 事件循环延迟 P99 | 91.816 ms | 88.539 ms |
| 192 次同类拒绝的完整诊断成员查询 | 192 次 | 12 次 |

无历史记录的一轮 CPU 耗时为 1702 → 1610 ms。查询计划同时确认 AUTO 更新使用复合主键，避免依赖计时噪声判断是否还会扫描该玩家的历史记录。

68 项回归检查和 5 个额外多人脚本通过，覆盖事务回滚、手动倍率、伪造请求、重复发奖、队友关注关系、连接代次、换场等待及结算生命周期。TypeScript 构建通过。

这些结果说明指定负载下减少了同步工作，不能承诺所有玩家请求都降低 12%，也不能推算云服最大在线人数。旧云服的结算延迟尖峰和 H400 根因仍需部署后的真实日志验证；现有每分钟 `[PERF]` 汇总继续保留。
