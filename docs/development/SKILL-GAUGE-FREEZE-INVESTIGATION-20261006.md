# 瞬时技能充能卡死排查

日期：2026-10-06。

状态：已从用户补充的组合中定位到充能与连击的双向反馈规则，真机卡死根因及修复仍待
验证。本轮没有修改技能数值、战斗逻辑、客户端、资源包或联机转发策略，没有生成
安装包，也没有部署修复；新增只读资源检查工具及对应测试。

## 玩家反馈

进入副本后，角色技能或装备效果造成瞬时大量技能充能，游戏出现卡死。
后续补充的例子是同队包含“天穹无坠之翼”和“白梅羽织的忍者武士”。
后者是斩铁的角色称号，不是另一件装备。目前仍缺完整主副角色、武器与魂珠配置、
关卡、客户端版本和卡死时刻，尚不能以该例子单独证明无限递归或具体渲染故障。

## 已核对的实现

### 服务器不执行逐帧技能槽计算

`src/multi/tcp/battle.ts` 和 `src/multi/tcp/relay.ts` 负责战斗消息转发、屏障及少量
状态通知，没有执行客户端 `MemberImpl` 的技能充能和特效逻辑。
因此，如果单人副本也会在同一组合下卡死，应优先排查客户端和能力数据。
多人消息拥塞仍需同一时刻的证据，不能仅凭历史服务器 CPU 高就判定本次原因。

### 原生充能已有聚合

公开 CN 客户端 `MemberImpl`：

- `reserveSkillPoint()` 将增量累加到 `reservedSkillPoint`，并非为每次增加建立队列对象。
- `update()` 把预留增量交给 `_addSkillPoint()` 后清零。
- `_addSkillPoint()` 除增加技能槽，还执行充能事件计数、统计及两个充能效果的显示。
- `applyInstantAbility()` 的百分比和固定值回槽分支，在预留回槽前还可能显示
  `AbilityPerpetuity` 效果。

这意味着“充能数值大”和“触发调用次数多”必须分开测量。数值一次增加很多，
不一定等价于执行很多次循环；反复触发能力和创建效果则可能消耗大量帧时间。
不建议未经测量新增另一套充能累加器，更不能声称聚合数值必然保留原事件次数语义。

### 特效和触发器存在需要验证的热点

公开客户端 `EffectManagerImpl.show()` 将相关充能效果交给 `addGeneralEffect()`，
后者创建 `SimpleEffect`，效果列表在更新、移动和回收阶段被遍历。
所检查的充能调用路径未显示按同一角色同一帧合并提示的处理。
这是可测量的优化候选，不是已证明的当前安装包缺陷。

`AbilityTriggerHandler.countHandler()` 根据事件累计次数与触发间隔计算次数，
可能在一次调用中循环执行多个能力。冷却大于零时有单次批量触发限制；
零冷却、高频事件及相互触发组合值得检查，但不能据此断言已经存在无限递归。
必须同时确认效果目标、触发来源、触发次数限制和条件，不能只看“SKILL”浮字数量。

## 建议的验证与修复顺序

1. 用具体队伍复现：区分单人/共斗、手动/自动，记录卡死前后技能槽、帧率、
   战斗计时和菜单响应。逐一替换可疑装备或角色定位来源，不全局削减充能。
2. 测量真实客户端：按帧汇总充能调用、触发器执行、活动特效数量和帧耗时，
   诊断必须有数量及时间上限，避免逐次打印反而放大卡顿。
3. 若瓶颈为演出：优先合并同角色同帧的充能视觉提示、复用效果，保留实际回槽、
   触发次数、统计和随机数调用语义；不能将所有效果或技能动画一概跳过。
4. 若为反馈连锁：先核对具体能力数据和预期冷却。增加冷却、触发上限或
   延后事件都会改变玩法与联机时序，需明确规则并验证多端一致性。
5. 若确认为数据配置错误：通过受控资源补丁修改准确条目；这与仅修改 Node
   服务器不同。只改服务端静态 JSON 不保证已下载资源的客户端同步变化。
6. 改客户端必须基于登记累计成品，Android 回读 SWF 方法差分，iOS 同时验证
   AOT；完成同队伍长局及多人一致性测试后才能认定修复可交付。

不建议以服务器丢弃技能消息、压低所有充能上限、踢掉高频玩家或删除玩家装备
作为本问题修复。这些方式可能造成不同步或改变玩法，且解决不了本地演出卡死。

### 已确认的关键词条

- 白梅斩铁：角色 `159998`，代码名 `samurai_robot_plum`，能力三 `1599983`。
  第一行仅主位生效，前提为编成中 `White` 组角色数量至少 6。
  瞬发触发 `141 / SkillGauge`，来源自身，每 1 次充能事件触发；
  效果 `226 / AddCombo`，追加 50～100 连击；冷却 0，次数上限 `(None)`。
  这里是“充能事件次数”，不是充满一次技能槽，也不是每增加 1%。
- 天穹无坠之翼：武器及对应魂珠 ID `100020`，`ability_soul` 第三行。
  前提 `39 / Flying`，每 30 连击触发，效果 `211 / SkillGauge`，
  目标 `5 / 全队`，等级插值 2%～10%；冷却 0，次数上限 `(None)`。
  魂珠沿用该表的低等级效果；触发结构相同，并非只有满破武器才可能参与反馈。
- 斩铁另有符合 6 光条件时队伍技能发动追加 10～15 连击、其他光角色技能发动给
  自身 5% 充能及追加 50 连击的规则。这些是可能的启动来源，需要完整队伍确认。

因此，仅把二者放在同队还不足以判断必现；应同时核对斩铁是否在主位、六个位置
是否满足客户端 `White` 编成判定，以及反馈发生时是否处于浮游。

### 反馈路径与不能越过的结论

```text
斩铁获得技能充能
  -> 能力三追加 50～100 连击
  -> 浮游时跨过天穹无坠之翼的 30 连击门槛
  -> 为全队充能，包含斩铁
  -> 后续充能事件再次触发能力三
```

在未达到连击上限且没有其他限制时，一次追加 100 连击会跨过 3～4 个 30 连击门槛，
具体取决于原有余数。单件满级武器可因此产生 3～4 次全队 10% 充能请求；
这是规则层面的计算，不是实测每帧调用数，也不代表最终技能槽可超过上限。
多份同类武器或魂珠可能增加请求，但不能把次数简单等同于斩铁能力三的再触发次数。

公开客户端补充核对了 `MemberAbilityTriggerImpl`、`BattleAbilityTriggerImpl`、
`ThresholdComboListener` 和 `ComboCalculatorImpl`：

- `_addSkillPoint()` 在技能槽入账前发出充能事件，即使槽已经满，也没有先检查
  本次实际增量是否为零。满槽本身不能作为“必然不再触发能力”的依据。
- 普通充能先累加进 `reservedSkillPoint`，在角色更新时合并入账。不能推导成每次
  武器请求都立刻递归执行一次斩铁能力，更不能直接声称指数增长。
- `addCombo()` 增加连击；常规连击门槛检查在战斗触发器更新中进行，连击减少时
  也会更新门槛。结合逐帧充能处理，这条路径可能形成跨更新的高频反馈。
- 公开实现有 9999 连击上限及关卡/状态连击限制。到达上限、失去浮游、角色死亡、
  连击重置等会影响反馈；因此不能声称无条件无限循环。
- 公开版本的枚举构造序号和当前主表数值并不一一相等，本次按构造名对应语义，
  没有把主表 `141` 直接当作公开 AS3 的 `case 141`。

当前结论比初查更具体：两条无冷却的效果构成高风险双向反馈，是该组合的首要排查
对象。尚未证明真机卡死最终发生在能力调度、特效更新、UI 文本还是其他队友技能。
此前 1047 的非法来源回槽过滤不一定会拦截这种规则允许的充能。

### 针对此组合的修复取舍

1. 先固定副本、客户端版本和完整队伍，比较原组合、移除所有天穹武器/魂珠、
   将斩铁从主位移到副位三种配置；另外观察非浮游时是否还复现。
   这些是待执行的真机对照，不是已通过的测试。
2. 若证实持续反馈是原因，可评估给能力三的“充能转连击”这一行增加局部冷却。
   原生数据字段即可表达，可走客户端资源增量更新，通常不需要重新安装 APK。
   它会减少该能力对其他合法来源的触发频率，因此属于明确的玩法调整；
   具体帧数必须经压测及用户确认，不能未经验证直接给定。
3. 更精细的方案是识别这条反馈链派生的充能，不再让它回触发原连击能力。
   现有回槽来源标签不等于完整的“连击来源链”；是否可仅用资源表达尚未证明，
   很可能需要客户端补充因果来源与多端一致性处理。不能冒称现有服务端已有此功能。
4. 纯特效合并可作为独立性能优化：保留充能和触发规则，只减少重复演出。
   如果真正瓶颈是能力反馈，仅隐藏 SKILL 浮字不能作为完整修复。
5. 不在 Node 服务端临时禁止该组合或踢人，也不改幻想装备准入豁免。
   只修改本地构建脚本、服务器 JSON 或重启服务器都不会自动改变玩家已下载的词条。
