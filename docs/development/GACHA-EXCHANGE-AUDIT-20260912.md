## 结论：H400 的直接原因是兑换标记不同步

暗龙存在于有效角色主表，当前角色稀有度为 5。在暗属性卡池 `219` 和 `1710` 中，它也存在于服务端 pool，但 `isExchangeable=false`；这两池共用的有效客户端 `black_element_pickup_05_character_4` 表则将它标为可兑换。

`src/routes/api/gacha.ts` 的 `/exchange_character` 使用 `getExchangeableGachaItem` 检查资格。该函数要求当前卡池中存在目标条目且 `isExchangeable=true`，并不按角色稀有度决定资格。上述组合会在发角色及扣积分之前返回 HTTP 400：`Character is not exchangeable from this gacha.`。这是可以复现 H400 的直接条件，不能简单归因为“没有加这个角色”。

全表发现 **432 个客户端可兑换、服务端不可兑换的卡池—角色关系，涉及 14 个卡池 ID、268 个不同角色**。这些角色均存在于相应服务端 pool，缺失的是正确的兑换资格。未发现相反方向的兑换标记差异；服务端额外出现而客户端没有的条目也都不可兑换。

## 隔离接口复现

读取当前 `out/routes/api/gacha.js` 实际路由和 `getGachaSync` 实际合并数据，通过 Fastify inject 执行，没有启动监听服务。使用新建的隔离数据库和测试账号，每个被测池均预置 250 积分。

- 432 个错误关系逐条请求，全部返回上述 HTTP 400。
- 每次失败后，积分仍为 250，角色状态不变。
- 对照：暗龙在 `170` 与 `990002` 可正常兑换，返回 HTTP 200、250 积分归零并获得角色。
- 对照：同一合法池只给 249 积分时，返回独立的 `Not enough exchange points.`，与本次资格错误区分。

这证明当前源码树存在该错误，不证明云端部署字节与本地相同，也没有代替用户手机实际操作验收。

## 同批发现的其他差异

1. **暗龙升星后，历史抽取分组没有同步。** 有效客户端有 82 个卡池关系仍将 261089 放在四星 odds 中；服务端其中 80 个关系也仍在四星 bucket，另两个关系缺失。角色主表则是五星。已检查的其他角色没有这种角色稀有度与池内星级不符的情况。此项影响抽取分组，与本次 H400 的直接兑换标记错误不同，不能靠放宽兑换检查解决。
2. **三个节日池的名单与客户端不同。** `1649`（十一黄金周2024）、`1675`（恭贺新年2025）、`1699`（五一黄金周2025）合计有 340 个仅在服务端出现的卡池—角色关系；后两个池还缺少客户端列出的 26 个关系，涉及 18 个角色，包括暗龙。这些差异条目均不属于可兑换项，因此不是上述 432 次失败的来源。
3. **9 个池存在真实的同星级内抽取比例差异。** 为 `214–219` 六个属性池及 `1649/1675/1699` 三个节日池。比较前已分别归一化桶内权重，排除了单纯整体缩放；按单项条件概率差大于 0.0001 判定。另有 `1710` 的整数权重原值不同，但归一化后差异未达到该阈值，未混算为上述 9 个池。
4. **其他标签差异。** 同一客户端可见条目中有 237 个 UP 标记、3 个限定标记与服务端不同；3 个限定差异均是角色 `211050` 在三个节日池中。它们不是兑换资格错误，但修正生成链时应一并核对。

全局普通抽取和十连保底的星级概率已与客户端 rarity odds 对照，没有超过服务端千分整数归一化容差（0.001）的差异。问题主要出在池内条目与标签，不是所有池的五星总概率都错了。

## 生成链的具体风险与修复边界

- `tools/rebuild_gacha_from_odds.cjs` 的 `accumulateElementRevival` 遍历全部 odds，用角色 ID 去重后保留第一次遇到的整条记录；它没有保留“这个目标池”的兑换、UP 和权重属性。相同角色在别的池不可兑换，并不代表本池也不可兑换。该逻辑能造成这里看到的属性池漂移；仅修最终 JSON 而不修此处，后续重建可能再次覆盖。
- 同函数仍使用角色 ID 首位推测星级；暗龙虽然保留 `261089` 这个 ID，当前角色主表已经是五星，不能再把 ID 前缀当成升星后的权威稀有度。
- `buildHolidaySyntheticPool` 在缺 odds 时按角色模板及日期拼池。现在有效 CDN 链已经能解析三个节日池的实际 odds，继续沿用过去的推测结果会与客户端名单不同。以上是当前代码路径与数据的审阅证据，没有重跑历史全量生成器来覆盖数据。

建议修复顺序：先依据当前有效客户端 odds 校正 432 个兑换标记，并加入所有卡池的客户端显示／服务端资格一致性回归；保留原有池边界、积分检查和刻意不可兑换的角色。随后单独统一历史升星分组、节日池成员及属性池权重，按同一权威数据生成两端内容，不用“全角色都允许兑换”掩盖差异。

修兑换标记本身可只改服务端 `assets/gacha.json`（本次 14 个问题池均由该文件提供），不必改客户端已正确的可兑换标记。若同时更改客户端升星分组或 odds，则需要匹配的 CDN 增量和 manifest。不要把这些尚未实施的修复写成已经进入当前 .106 包；.106 仍是此前已完成的入手方法补全包。
