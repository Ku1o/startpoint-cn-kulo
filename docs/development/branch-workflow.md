# 固定开发、分支与交付流程

本文是 StarPoint CN 的长期协作约定。目标是让不同 Codex 会话采用同一套安全流程，同时保护本地未提交修改、运行数据和云服务器状态。

## 1. 固定角色

| 对象 | 固定用途 |
| --- | --- |
| `F:\codex\startpoint-cn-private-clean` | Git 源仓库，所有可提交修改的唯一真源 |
| `staging` | 长期保留的开发、集成、试运行与交付分支 |
| `main` | 已经过观察验证的稳定分支 |
| `F:\startpoint-cn-main` | 本地运行镜像，非 Git 仓库，含本机环境与运行状态 |
| `F:\codex\outputs\server-overlays` | 云服务器覆盖整合包的默认输出目录 |

`staging` 不是一次性修复分支，不在合并后删除。`F:\startpoint-cn-main` 不是源码真源，禁止用它反向覆盖 Git 仓库。

## 2. 用户口令的默认含义

- “提交”“推送”“提交本地更新”：只提交当前任务文件并推送到 `origin/staging`，随后对可部署修改执行本地运行目录同步；不会自动制作云服务器整合包。
- “分类提交”：按功能大类拆成多个独立 commit，每个 commit 只包含该类实现、必要资源和配套记录；不得只在一个 commit 的说明里分类。本规则来自用户 2026-09-13 的明确要求，后续提到“分类”时持续适用。共享 manifest 按各类分包逐步更新，最终交付使用完整版本。
- “做整合包”“打包”：才允许制作云服务器覆盖整合包。默认汇总自上一个由用户明确要求制作的整合包之后的全部可部署修复；用户指定提交或文件范围时按指定范围执行。未经用户要求而偶然生成的 ZIP 不作为下一次汇总的起点。
- “合并到主分支”“正式发布”：才允许创建 `staging -> main` 的 PR、等待检查并合并。
- “只同步”或“只打包”：按字面只执行指定步骤，不擅自提交、推送或合并。
- “部署到云服务器”：需要单独明确授权；生成覆盖包不等于上传、解压或重启线上服务。

## 3. 每次开始任务

1. 确认正在 `staging`，并确认上游为 `origin/staging`。
2. 记录分支、HEAD、远端分歧、暂存文件、未暂存文件和未跟踪文件。
3. 把任务开始前已存在的所有修改视为用户资产；当前任务不得顺手整理或提交。
4. 拉取远端引用，检查 `main` 与 `staging` 的关系。若更新分支可能触碰脏文件，先停止并说明，不自动 stash、reset 或 clean。

## 4. 修改、验证与提交到 staging

1. 只修改本次需求涉及的文件。
2. 运行与风险相称的测试、类型检查和构建。修改 TypeScript 且云端使用 `out/` 时，必须生成并核对相应 JavaScript 产物。
3. 用明确路径逐个暂存；禁止 `git add .` 和 `git add -A`。
4. 提交前检查暂存 diff，确保没有混入用户原有修改、密钥、数据库、日志或临时产物。
5. 每个任务提交都必须同时包含清晰的标题和正文，不得只写一行标题。正文至少记录：
   - 本次具体更新或修复了什么；
   - 修改原因、原问题或关键行为变化。
6. commit 的标题和正文中禁止写入验证命令或结果、测试、构建、CI 状态、基准测试、耗时、覆盖率数字，以及 `Verified with` 等同类表述。此规则同样适用于纯文档和纯指令提交，不得添加 `tests not run` 等模板文字。上述信息只写在最终交付报告中。
7. 提交正文必须以实际暂存内容为准，不得写入未完成、未验证或不属于本提交的工作。
8. 提交到 `staging`，推送 `origin/staging`，并在最终交付报告中记录提交哈希、完整提交说明和 CI 结果。

## 5. 确定“本次发布文件集”

发布文件集以本次任务在 `staging` 上的已提交内容为基准，而不是以整个脏工作区为基准。

- 服务端源文件变更：包含源文件和实际发生变化的对应 `out/` 产物。
- 游戏数据或资源变更：包含所需 JSON、清单和补丁 ZIP。本地运行同步清单与云服包清单分别确定；云服包按第 7 节排除 `production` 散资源，不能直接沿用旧的本地同步清单。
- 依赖变更：包含 `package.json` 与 `package-lock.json`，并在部署说明中写明安装命令。
- 文件删除：作为发布动作显式记录；本地镜像删除前必须备份原文件。
- 文档、测试、Codex 指令和本地开发工具默认不进入云端包，除非它们本身就是交付物或云端运行必需。

若某个发布路径在提交后又存在未提交编辑，必须从目标提交中导出确定版本，不能直接复制工作树中的混合内容。

## 6. 同步到 `F:\startpoint-cn-main`

1. 为本次同步创建 `F:\startpoint-cn-main\.codex-backups\<时间>-<主题>\`。
2. 对每个即将覆盖或删除的目标文件，先按原相对路径备份。
3. 只复制发布文件集中的明确路径，禁止对项目根执行镜像同步。
4. 默认保留以下本地状态：`.env`、`.database/`、基础 `.cdn/`、日志、`node_modules/`、`work/`、本地工具和已有备份。
5. 逐个校验同步后目标文件与提交版本的字节或哈希一致。
6. 报告已复制、已删除、已备份、跳过和发生冲突的路径。

## 7. 生成云服务器覆盖整合包

默认产物目录：`F:\codex\outputs\server-overlays`。

本节只在用户明确提出“做整合包”“打包”或同等要求时执行。单次修复、提交、推送、同步运行目录或重启服务都不自动触发整合包制作。

整合包规范：

- 名称：`startpoint-cn-cloud-overlay-<主题>-<YYYYMMDD-HHMMSS>.zip`。
- ZIP 内直接使用仓库相对路径，不增加额外顶层文件夹。把 ZIP 解压到云服务器项目根即可覆盖。
- 内容来自“本次发布文件集”中允许进入云服包的路径，且来自已提交版本或已验证构建产物。
- 用户于 2026-09-11 明确要求云服包不打 `production` 散资源：外层 ZIP 排除 `production/**` 和 `assets/asset-patch/production/**`，包括 upload、medium_upload、android_upload、ios_upload。客户端资源通过启用的 `assets/asset-patch/active/*.zip` 和 manifest 交付，禁止把内层分包再解出一份散资源塞进外层包。内层分包自身的 `production/` 是必要格式，须逐字节保持，不在内层做这项过滤。
- 历史整合包、审计、生成脚本或本地同步清单曾包含散资源，不构成继续打包的依据；每次打包均须检查上述排除项。除非用户以后明确要求恢复打包，否则持续遵循。本规则不授权删除源码、本地运行目录或 `.cdn` 中已有资源。
- 禁止包含 `.env`、数据库、日志、密钥、备份、`node_modules`、本地工作目录及无关文件。
- 检查所有成员均为安全相对路径，无盘符、绝对路径或 `..` 跳转。
- 打包后重新读取每个成员，与源文件逐字节比较，并计算 ZIP 的 SHA-256。

与 ZIP 一起提供：

- `<包名>.files.txt`：完整成员清单；
- `<包名>.sha256.txt`：SHA-256；
- `<包名>.部署说明.txt`：适用提交、备份方法、覆盖位置、是否需要安装依赖/构建、重启方式、验证方法和回滚提示。

只生成覆盖包，不自动连接或修改云服务器。

## 8. 观察期与合并 main

1. 在 `staging`、本地运行镜像和需要的测试环境中观察。
2. 用户明确确认可以正式合并后，创建 `staging -> main` PR。
3. 等待卫生检查、测试和其他必需检查通过，再合并到 `main`。
4. 合并后将 `staging` 快进到最新 `main` 并推送；保留 `staging`。
5. 若分支出现双向提交或冲突，先展示分歧和方案，不强推、不静默改写历史。

## 9. 完成交付时必须报告

- 当前分支、提交哈希和远端同步状态；
- 执行过的测试、构建和 CI 结果；
- 同步到 `F:\startpoint-cn-main` 的精确路径及备份目录；
- 仅当用户明确要求并实际制作整合包时，报告云服务器 ZIP、文件清单、部署说明和 SHA-256 的绝对路径；否则说明本次未要求、未制作整合包；
- 未处理或仍留在工作区的用户修改；
- 尚未执行的步骤以及原因，尤其要明确说明是否尚未合并 `main`。
