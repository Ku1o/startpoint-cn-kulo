# Windows 文件检查泄漏与存储 SQL 复用

Windows Node.js 20.20.2 的 `fs.existsSync()` 在访问已存在路径时，先执行 `uv_fs_access`，随后对同一个请求结构执行 `uv_fs_stat`，退出时才清理请求。第二次初始化覆盖第一次分配的路径缓冲区，造成不受 JavaScript GC 管理的原生内存泄漏。对应实现见 [Node 源码](https://github.com/nodejs/node/blob/v20.20.2/src/node_file.cc#L1017) 和 [Windows libuv 路径分配](https://github.com/nodejs/node/blob/v20.20.2/deps/uv/src/win/fs.c#L224)。

`src/lib/file-exists.ts` 在 Windows 上改用一次 `statSync` 判断存在性，并保留异常返回 false、跟随链接目标的行为；其他平台沿用原生接口。服务端资源、配置、种子备份、账户状态及后台线程入口使用此辅助函数。没有全局修改 Node fs 模块，也不缓存检查结果，文件创建、替换和删除仍立即生效。

`src/lib/storage-layout.ts` 将存储布局检查及紧凑任务计数写入的重复 SQL 编译接入已有的每连接有界 statement 缓存。缓存编译语句而非查询结果，保留运行期间的迁移状态变化、事务回滚、连接隔离和参数绑定语义。

两项修改不改变数据库结构、存档格式、玩家归属、奖励规则、资源版本或客户端准入配置。部署需要源文件及对应 out 文件，尤其不能遗漏新增的 `out/lib/file-exists.js`；无需安装依赖或数据库迁移，替换后需要重启服务。已泄漏的内存不会因覆盖文件而自动释放。

## 验证范围

- 同版 Windows Node 二进制对已存在文件执行 100 万次检查，原生 existsSync 的 RSS 从约 24 MiB 增到 168 MiB，强制 GC 后仍持续增长；实际编译后的辅助函数约保持 30 MiB。不存在路径的原生接口对照也保持稳定。
- 文件检查覆盖中文路径、文件及目录、Buffer/URL 参数、实时创建/替换/删除、错误输入、权限失败、失效目录链接，以及绕过泄漏的原生调用。
- SQL 覆盖重复写入的编译复用、玩家参数隔离、add/max/min、迁移表变化、事务回滚及连接隔离；种子持久化、资源路由、准入、worker 存档导出、账号切换及公告集成检查通过。
- 原生快照中存在性检查的存活分配持续增加，与上述缺陷一致；这不证明所有进程内存增长都来自该接口。长时间运行仍应结合 JS 堆、原生分配及进程私有内存共同评估。

独立的 SQL 优化用于减少分配和 CPU 消耗，不替代文件检查泄漏修复。仅含本批服务器修复的覆盖包应沿用现有配置和资源，不携带数据库、准入密钥、运行日志或历史资源分包。
