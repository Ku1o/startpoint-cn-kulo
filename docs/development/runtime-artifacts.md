# 服务端运行产物与云服覆盖包

Git 保存服务端源码、引用的数据、依赖锁文件和编译策略，生成的 `out/` 只用于本地运行及交付。云服包仍包含必要运行产物，部署不要求现场编译。取消 Git 跟踪只影响版本控制，不能删除本地运行目录或形成云端删除指令。

## 开发与提交

从 Git 获取源码后先执行 `npm ci`、`npm run build`。Windows 日志启动入口使用已有 `out/`，不会自动编译；源码或依赖改变后应重新生成本地运行产物。普通重启复用已验证且输入未变的产物。

暂存明确源码路径后执行 `node tools/check-out-artifacts.cjs`。检查隔离编译实际 Git index 输入，避免未暂存的依赖掩盖遗漏；`--worktree` 只检查开发状态。生成的 `out/` 不暂存。CI 通过锁文件安装依赖并检查完整服务端编译及相关工具回归。

`npm run build` 还生成旧页面 CSS，管理后台另有独立编译。云服固定提交构建会从同一提交的 `admin/` 输入执行后台编译，并将 `web/dist/` 与服务端 `out/` 一起纳入运行产物清单；本地已有的 `web/dist/` 不作为交付来源。旧页面 CSS 仍按原有提交范围处理。

## 固定提交生成与封包

`tools/runtime-build-policy.json` 标记源码构建模式，并规定工具链与必须的动态运行入口。打包器根据 `--source` 和 `--base` 解析的提交选择输入，不读取当前脏源码或本地旧 `out/`。

构建器隔离导出源码、引用的 JSON、编译配置、依赖定义及策略，使用锁定依赖完整编译，禁用增量缓存并禁止错误发射。完整发射清单必须覆盖普通模块及 worker、转发子进程等动态入口；失败或缺少必要成员时拒绝封包。管理后台从该提交的独立锁文件执行 `npm ci` 和 `npm run build`，检查 `web/dist/index.html`、全部输出成员及路径安全性。运行 JSON 包括明确引用的 `docs/generated/character_table.json`，不会把其他文档一起装入。

正式生成默认隔离执行 `npm ci --ignore-scripts`。`--dependency-root` 用于显式受信安装目录的复用：核对源锁文件、安装锁元数据及实际包版本，不证明包内每个字节未经本地修改。构建身份注明依赖来自 fresh npm ci 或受信本地安装；正式交付默认使用前者。策略固定 Node、npm、TypeScript 版本；工具链不匹配时停止，不能借用另一版本重建历史基线。

两端 `out/` 与 `web/dist/` 完整运行产物按集合与实际字节比较，包含间接影响和新增依赖；静态资源及脚本沿用提交差异与既有排除规则。内容索引声明的三个生成器 `tools/build-content-discovery.cjs`、`tools/build-content-discovery-gacha.py`、`tools/build-content-discovery-rewards.cjs` 和部署操作文档明确列入静态候选范围，其他 `tools/` 文件仍不因此进入包。索引或其绑定来源更新时，打包器逐一核对索引声明的全部来源路径及目标提交字节摘要，并要求已变更的来源进入包；目标服务器的部署检查仍独立校验全部来源字节。CDN 内层 ZIP 保持原字节，外层 loose production、config、环境、存档、日志及密钥继续排除。ZIP 成员集合、安全路径、CRC 和逐成员字节均核验后，才生成交付身份；只提供整包 SHA-256 与路径/大小清单。

## 迁移、删除与回滚

无构建策略的历史提交继续读取该提交保存的 `out/` 字节，避免将重新编译的结果当作当时交付的版本。源码构建提交的两端分别按其固定输入生成；跨越迁移提交时，即使 Git 中 `out/` 消失，只要目标编译仍产生文件，就不是运行删除。

部分历史提交没有保存完整 `out/`。回滚遇到这些缺失记录时，只有完整编译输入集合与字节身份相同，才能保留当前生成的缺失成员，并明确记录其来源；输入改变且目标源码仍需要未保存的历史产物时，拒绝封包，需要另行提供可核验的历史运行产物。不能把 Git 未跟踪当成运行文件不存在，也不能用当前工具链猜测旧交付字节。只有配置身份相同、实际根目录为 `src` 且目标源码确实移除的明确映射，才能形成相应候选删除。

只有运行文件在目标集合中实际消失，才列入候选删除清单。覆盖包不自动删除云端文件，执行删除仍按部署规则备份并单独授权。历史标签和提交保持原样，不改写共享历史。回滚继续使用 `--base` 指定当前版本、`--source` 指定目标版本，无需切换工作区。

发布记录分别注明静态提交来源、生成物构建身份和整包身份，不把生成物声称为 Git blob。正式交付基线、同批完整替代、标签发布、上传和部署边界沿用[分支与交付流程](branch-workflow.md)。

## 只交付服务端修复

需要保留旧 CDN 和内容数据时，不能将最新服务端整体编译后仅删除 active ZIP。新 manifest 会宣告尚未交付的资源版本，而角色、道具、商店等非 ZIP 权威数据和服务端玩法代码也可能依赖新资源。

`build-cloud-overlay.py --selection-plan <JSON>` 使用 `schema: 1`、`kind: "server-fixes"`、完整 `base_commit`、`source_commit` 和按采用顺序排列的 `selected_commits`。来源锚点及所选提交必须来自同一主线历史；只将选定提交相对其第一父提交的差异应用到隔离 Git index。禁止资源、客户端、配置和依赖变更混入修复配方。应用失败即停止，不从当前工作区补文件。

组合输入以完整 Git tree OID 固定，不创建额外源码提交，不移动分支或主工作区 index。隔离编译器的 `--source` 仍标识既有来源锚点，`--source-tree` 明确标识实际组合输入；身份同时记录二者，不能把组合内容声称为锚点提交的完整树。Git tree 可由保留的基线、所选提交和配方重新生成。

成员、删除清单和编译产物都从原基线与组合树比较。包外保留选择配方与暂缓清单，正式标签说明该批只交付所选范围；包内不放协作台账、过程说明或测试工具。可用 `--verification-root <空目录>` 保留两端的完整编译输出供隔离回归，默认临时构建仍自动清理。

部分交付台账分别记录服务端组合树、内容与 CDN 的原基线，以及从组合树到来源锚点尚未交付的文件。整仓 `included_through_commit` 保持完整覆盖的旧基线，不能推进成来源锚点。后续普通整仓打包遇到部分交付记录应停止，先根据实际分面范围明确增量，防止遗漏暂缓内容或用全量假设覆盖已采用修复。交付与云端实测部署继续分别记录。
